## 1. 一句话版本（项目列表项）

> **机器人 TCP 实时控制上位机（Linux C11 / POSIX，独立开发）**
> 用纯 C11 + POSIX API 重写原 Qt/C++ 通信上位机，零第三方依赖；
> 在 Linux 6.8 / x86_64 / CFS 调度下对 10ms 控制线程完成 4 场景 × 10000 周期调度测量，
> 相邻周期偏差 P99 = 0.12~0.48 ms（占满 12 核时恶化至 3.30 ms），
> 并通过绝对时间定时将 start-to-start 平均间隔从 10.152 ms 收敛到 10.000005 ms；
> 为帧尾同步的粘包状态机建立 16 类可复现测试，10000 帧固定种子随机分块解析正确率 100%，
> 并用 ASan/UBSan 排查内存越界。

## 2. 分条描述（按简历 bullet 组织，每条都带证据锚点）

### 2.1 周期调度测量

- 在**非实时 Linux 内核（6.8.0-138-generic，CFS 调度，未用 root/SCHED_FIFO）**下，
  对 10ms 控制线程开展 **10000 周期 × 4 场景** 调度测量：
  - 空载：相邻周期偏差 **P99 = 0.481 ms**，最大工作耗时 **0.108 ms**；
  - 真实业务收发（loopback 每 10ms 一帧上行）：偏差 **P99 = 0.452 ms**，最大工作耗时 **0.135 ms**；
  - 占满 12 核 CPU 负载：偏差 **P99 = 3.295 ms**，最大工作耗时 **4.003 ms**，
    其中 **888/9999 个周期偏差超过 1 ms**；
  - 改用绝对时间定时（`TIMER_ABSTIME`）：偏差 **P99 = 0.122 ms**，唤醒延迟 **P99 = 0.177 ms**。
  - 证据：`results/03_periodic_timing_*.csv`、`logs/analyze_timing.log`
  - 命令：`bash performance_evaluation/scripts/run_all_bench.sh 10000`

- 通过测量定位到**相对 `clock_nanosleep` 的累积漂移**：三个相对睡眠场景的相邻周期偏差
  **全部为正**，`start-to-start` 平均间隔为 **10.152 ~ 10.298 ms**（比目标长 1.5%~3.0%），
  实测频率约 **97.0~98.5 Hz** 而非标称 100 Hz；改为绝对时间定时后平均间隔为 **10.000005 ms**。
  - 证据：`source_audit.md` 第 3 节（源码分析）+ 上表（实测验证）

### 2.2 协议解析状态机测试

- 为**基于帧尾标志（0x55 0x56）的 TCP 粘包/半包解析状态机**新增 **16 类自动化测试**，
  测试二进制**直接编译生产解析器源码**（不重写第二份解析器）；
  在 **10000 帧固定随机种子（1~17 字节随机分块）** 测试中通过 **10000/10000 帧，
  正确率 100%**，并逐帧比对内容而非仅计数。
  - 覆盖：单帧/粘包/半包/垃圾前缀/错误帧尾/帧头未知/超长洪泛/连接中途关闭/帧尾字节出现在 payload
  - 证据：`results/03_parser_tests.csv`
  - 命令：`make test`

- 使用 **AddressSanitizer + UndefinedBehaviorSanitizer**（`-fsanitize=address,undefined`，
  `detect_leaks=1`）对解析器路径进行插桩运行，**未观察到越界访问、未定义行为或内存泄漏**。
  - 命令：`make test-asan`
  - 诚实边界：ASan 未报警≠形式化证明；且只覆盖协议解析路径，未对完整程序插桩。

- 通过代码审计发现并**如实记录**该协议的两个真实约束（未擅自更改协议）：
  协议**无 CRC/校验字段**，无法检测载荷内容损坏；
  当 20 字节窗口帧尾恰为 `0x55 0x56` 而帧头既非 `'u'` 也非 `'c'` 时该 20 字节被静默丢弃。
  - 证据：`src/robot_protocol.c` + 用例 T08

### 2.3 socket 端到端模拟验证

- 编写 loopback 模拟机器人服务端，**逐帧校验上位机下行控制帧**：
  4 个场景合计 **40000/40000 帧格式合法（100%）**，`seq` 序列号**跳变 0 次**。
  - 证据：`results/03_mock_server_*.csv`
  - 边界：这是离线 TCP 模拟，**不代表真实机器人闭环控制测试**

### 2.4 缺陷修复

- 通过审计与实测复现定位退出挂死缺陷：接收线程阻塞在无超时的阻塞式 `recv` 上，
  SIGINT 被其他线程收走且对端静默时，`pthread_join` 永久挂起（基线版本 6 秒未退出，需 `kill -9`）。
  在 `join` 前增加 `shutdown(g_sockfd, SHUT_RDWR)` 唤醒阻塞读，A/B 实测退出时延
  **从"挂死"降至 0.102 s**。
  - 证据：`results/03_sigint_hang_baseline_before_fix.txt` / `..._after_shutdown_fix.txt`

- 验证断线检测行为：对端 FIN 与 RST 两种断线方式下上位机均在 ~2.0 s 内自行识别并退出（退出码 0）；
  同时明确能力边界——**未实现自动重连**，且 `SO_KEEPALIVE` 使用内核默认参数（约 7200 s），
  **不等价于及时断线检测**。
  - 证据：`results/03_disconnect_tests.csv`

### 2.5 资源稳定性

- 在**loopback 持续收发工况**下**连续运行 30 分钟**（每 5 s 采样 `/proc/<pid>/status`
  与 `/proc/<pid>/fd`，共 360 个采样点），期间完成 **177108 帧控制帧下行 + 180456 帧状态帧上行，
  坏帧 0、序列号跳变 0**；
  记录 **VmRSS 全程恒定 2016 kB（变化量 0）**、**线程数恒为 3**（主 + 发送 + 接收）、
  **文件描述符数恒为 19**，未观察到任何增长。
  - 证据：`results/03_resource_usage_soak.csv`、`logs/soak_run.log`
  - 命令：`bash performance_evaluation/scripts/run_soak.sh 1800 5`
  - **诚实边界：只写"未观察到增长"，不写"无内存泄漏"**（有限时长观察不能替代 Valgrind 全量检查）

### 2.6 工程化

- 在**不改变默认通信行为**的前提下新增可选测量开关
  （`--benchmark / --metrics-csv / --cycles / --abs-timer`），
  测量代码采用**预分配采样数组 + 运行期零 IO + 退出时统一导出 CSV**，
  避免 printf / 磁盘 IO 污染被测周期；并保证测量路径单写者、无数据竞争。
- 保持 **ARM 交叉编译可用**（`make cross-check`，arm-linux-gnueabihf-gcc 4.9.4 编译通过），
  未修改任何设备树或内核驱动（本项目为纯用户态工程）。
  - 证据：`modification_report.md`、`make cross-check` 输出

## 3. 面试可能追问的问答准备（基于实测事实，不夸大）

**Q：10ms 任务做到什么精度？是硬实时吗？**
> 不是。普通 Linux + CFS 只能做到"统计意义上的亚毫秒抖动"。
> 我实测空载下相邻周期偏差 P99 是 0.481 ms，占满 12 核时恶化到 3.295 ms，
> 所以我在报告里明确写了"这不是硬实时，唤醒延迟也不等于端到端执行器延迟"。
> 如果要做硬实时，需要 PREEMPT_RT + SCHED_FIFO + CPU 隔离，那是另一个课题，我没有做，也不会声称。

**Q：为什么相对睡眠会有漂移？**
> `clock_nanosleep` 传 flag=0 时 `req` 是相对时长，睡眠从"调用时刻"起算，
> 所以实际周期 = 目标周期 + 该周期的组帧与 send 耗时。我实测三个相对睡眠场景的
> 相邻周期偏差**全为正**，start-to-start 均值 10.152~10.298 ms，正好印证这一点。
> 改成 `TIMER_ABSTIME` 后每周期都睡到绝对目标时刻，平均间隔回到 10.000005 ms。

**Q：怎么保证测量代码不干扰被测对象？**
> 三点：采样数组在启动时一次性 `calloc`，运行期不再分配；
> 运行期不打印不写文件，只在退出时统一导出 CSV；
> 打点只有两次 `clock_gettime(CLOCK_MONOTONIC)`，而且只有 `--benchmark` 打开才生效。

**Q：协议解析器你怎么验证的？**
> 直接把生产源码 `src/robot_protocol.c` 编进测试二进制，没有重写第二份解析器。
> 16 类用例，其中最强的一条是 10000 帧固定种子、1~17 字节随机分块，
> 逐帧比对类型和字段值，10000/10000 通过。另外用 ASan+UBSan 跑了一遍。
> 同时我也如实记录了协议没有校验字段，无法检测载荷损坏——这是协议本身的约束，不是我漏做。

**Q：项目有什么已知不足？**
> 四个：没有断线重连；没有应用层心跳；`SO_KEEPALIVE` 用内核默认参数（约 7200 s），
> 拔网线不会及时报错；协议无校验字段，且存在"帧头未知但帧尾合法时静默丢 20 字节"的窗口。
> 这些都是我审计出来并写进报告的，没有为了好看而隐藏。

## 4. 禁止使用的表述（本项目中均无实测支撑）

| 禁止表述 | 原因 |
|---|---|
| "微秒级实时调度" / "硬实时" / "实时性达到微秒级" | 实测是亚毫秒级统计抖动，非实时内核非实时调度 |
| "丢包率为 0" / "100% 可靠" | 未在真实网络下测丢包；协议无校验字段，不能声称数据可靠 |
| "车规级通信" | 无任何车规标准符合性验证 |
| "支持自动重连" | **未实现** |
| "跨平台部署到 i.MX6ULL/ARM 板并完成实测" | 仅完成 ARM 交叉编译的**编译**验证，无板端运行数据 |
| "使用 CRC 校验保证数据完整性" | 协议无 CRC，未实现 |
| "无内存泄漏" | 仅有有限时长 RSS 观察曲线 + ASan 覆盖协议解析路径，不足以断言 |
| "TCP_NODELAY 降低了网络延迟 X%" | 未做开启/关闭对照实验 |
| "开发了 Linux 内核驱动 / V4L2 摄像头 / 设备树移植" | 本项目为纯用户态程序，源码中无相关内容 |
