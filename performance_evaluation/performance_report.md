## 1. P0-A：10ms 周期任务实测结果

### 1.1 统计口径

```
work_ns           = end_ns - start_ns                    （组帧 + send，不含 sleep）
period_dev_ns     = (start_ns[i] - start_ns[i-1]) - 10ms （相邻周期偏差）
wake_delay_ns     = start_ns - scheduled_ns              （仅 --abs-timer 模式）
周期超期          = end_ns > scheduled_ns + 10ms          （仅 --abs-timer 模式可判定）
百分位            = 最近秩法 nearest-rank（脚本与程序内置算法一致）
时间戳            = clock_gettime(CLOCK_MONOTONIC)，64 位纳秒
```

- 每场景 **10000 周期**（10ms × 10000 ≈ 100 秒），样本全量落盘，**无丢样**
  （`dropped=0`，`samples=10000`）。
- 运行期循环内**无任何 printf / 文件写入**，不污染测量。

### 1.2 主结果表（10000 周期 / 场景）

| 场景 | 定时模式 | work p50 | work p99 | work max | 周期偏差 mean(\|d\|) | 周期偏差 p95 | **周期偏差 p99** | 周期偏差 max | start-to-start mean |
|---|---|---|---|---|---|---|---|---|---|
| idle（空载） | relative | 24.8 µs | 79.2 µs | 0.108 ms | 257.6 µs | 449.9 µs | **0.481 ms** | 1.198 ms | 10.2576 ms |
| traffic（真实业务收发） | relative | 22.8 µs | 79.8 µs | 0.135 ms | 152.0 µs | 401.9 µs | **0.452 ms** | 0.542 ms | 10.1520 ms |
| load（占满 12 核） | relative | 13.1 µs | 2454.3 µs | 4.003 ms | 298.6 µs | 2278.2 µs | **3.295 ms** | 10.265 ms | 10.2986 ms |
| traffic | **absolute** | 10.1 µs | 30.9 µs | 0.053 ms | 12.3 µs | 56.5 µs | **0.122 ms** | 0.178 ms | **10.000005 ms** |

唤醒延迟（仅绝对定时模式）：mean = 66.3 µs，p95 = 106.7 µs，**p99 = 176.9 µs**，max = 232.6 µs。

**超限次数**

| 场景 | 周期偏差 > 1 ms | > 5 ms | > 10 ms | 工作耗时 > 10 ms | 发送错误次数 | 周期超期 |
|---|---|---|---|---|---|---|
| idle/relative | 1 | 0 | 0 | 0 | 0 | N/A（无独立 deadline） |
| traffic/relative | 0 | 0 | 0 | 0 | 0 | N/A |
| load/relative | **888** | **25** | **1** | 0 | 0 | N/A |
| traffic/absolute | 0 | 0 | 0 | 0 | 0 | **0** |

**原始数据**：`results/03_periodic_timing_{idle,traffic,load}_relative.csv`、
`results/03_periodic_timing_traffic_absolute.csv`（各 10000 行，含全部时间戳）。
**独立复算日志**：`logs/analyze_timing.log`（脚本复算结果与程序内置汇总逐项一致）。

### 1.3 结论

1. **相对睡眠存在系统性正向漂移，且与源码分析完全吻合。**
   三个 relative 场景的相邻周期偏差**全部为正**（最小值 +16.6~+19.3 µs），
   `start-to-start` 平均间隔为 **10.152 ~ 10.298 ms**，即比 10 ms 目标长 **1.5% ~ 3.0%**。
   原因就是审计指出的：`clock_nanosleep(CLOCK_MONOTONIC, 0, ...)` 是相对睡眠，
   实际周期 = 10 ms + 本周期组帧与 send 耗时（+ 内核定时器向上取整）。
   → **不能用"10ms 周期任务"直接推导"实际频率 100 Hz"**；实测约 **97.0 ~ 98.5 Hz**。

2. **改成绝对时间定时（`TIMER_ABSTIME`）后漂移被消除。**
   同一场景对比（traffic）：`start-to-start` 平均间隔从 **10.152 ms → 10.000005 ms**
   （偏差从 +152 µs/周期 → +5 ns/周期）；周期偏差 P99 从 **0.452 ms → 0.122 ms**（降低 73%）；
   中位数偏差从 +100 µs → **−22 ns**。这是本次唯一被实测证明有效的性能改进。

3. **CPU 竞争是非实时 Linux 上抖动的决定性因素。**
   占满 12 核后：周期偏差 P99 从 0.452 ms 恶化到 **3.295 ms（×7.3）**，
   最大偏差 10.265 ms（出现 1 次超过一个完整周期），
   工作耗时最大值从 0.135 ms 恶化到 **4.003 ms（×30）**。
   分布呈明显双峰：`p50≈13 µs` 但 `p99≈2.45 ms`，
   说明绝大多数周期很快，但约 8.9%（888/9999）的周期被 CFS 抢占推迟 >1 ms。

4. **本场景下工作耗时（组帧+发送 20 字节）始终远小于周期预算**（p99 ≤ 79.8 µs，最恶劣 4.0 ms），
   因此周期偏差主要来自**调度唤醒**，而不是业务逻辑本身。

### 2.2 结论与诚实边界

1. 粘包 / 半包 / 任意分块 / 垃圾前缀 / 坏帧尾 / 超长输入 / 中途关闭等场景**均可正确恢复**，
   且在 ASan+UBSan 下**未观察到越界或未定义行为**。
2. **协议没有校验字段**（无 CRC、无 checksum），因此**无法检测载荷内容损坏**
   （位翻转、内容截断但长度恰好对齐）。**不得声称具备数据完整性校验能力。**
3. **已固化的实现缺陷（如实记录，未擅自改协议）**：
   当 20 字节窗口的帧尾恰好等于 `0x55 0x56` 但帧头既非 `'u'` 也非 `'c'` 时，
   这 20 字节被**静默丢弃**，且该窗口可能吞掉紧随其后的真实帧起始字节。
   在含 `0x55 0x56` 的随机载荷下这类窗口概率约 1/65536 量级，工程上可接受，
   但**不能宣称解析器"零丢帧"**。用例 T08 固化了该行为。
4. ASan "未报警" **不等于形式化证明**，只说明在本组用例下没有发现问题。

## 4. P1：断线检测与资源稳定性

### 4.1 断线检测（原始数据：`results/03_disconnect_tests.csv`）

| 子场景 | 服务端行为 | 上位机退出码 | 运行时长 | 是否检测到断线 |
|---|---|---|---|---|
| fin | 推 200 帧后优雅关闭（FIN） | 0 | 2.000 s | ✅ `recv: connection closed by peer` |
| rst | 推 200 帧后 RST 强断 | 0 | 2.001 s | ✅ `recv: Connection reset by peer` |
| silent + SIGINT | 只接不发，2 s 后发 SIGINT | 0 | 2.104 s（含 2 s 等待） | ✅ 立即退出 |

- 三种情况下上位机均**主动、干净地退出**，无残留进程、无 `kill -9`。
- **能力边界**：程序**没有断线重连**，断线即整体退出；本次**未新增重连模块**。
- **空闲断线检测能力有限**：`SO_KEEPALIVE` 已开启，但未设置 `TCP_KEEPIDLE/KEEPINTVL/KEEPCNT`，
  使用内核默认（约 7200 s 空闲后才开始探测）。**`SO_KEEPALIVE` 不等于及时断线检测**，
  拔网线场景下不会在秒级内发现。

- **socket 层实测证据**（`logs/06_socket_observation.log`，soak 运行中抓取）：
  ```
  ss -tiop | grep -A1 robot_linux_app
  ESTAB ... users:(("robot_linux_app",pid=46933,fd=3)) timer:(keepalive,113min,0)
       ts sack cubic wscale:7,7 rto:204 ... bytes_sent:815480 bytes_acked:815481
       bytes_received:825100 ... data_segs_out:40774 data_segs_in:41255 minrtt:0.013
  ```
  - `timer:(keepalive,113min,0)` —— **内核保活探测定时器还剩 113 分钟**，
    直接坐实"SO_KEEPALIVE 使用默认 7200 s 参数、无法及时发现空闲断线"这一审计结论。
  - `bytes_sent:815480 ÷ 20 B = 40774 = data_segs_out` —— 与发送帧数**完全一致**，
    证明下行控制帧确实是每帧 20 字节、未发生合并/拆包异常。
  - `minrtt:0.013 ms`（loopback）说明**本环境不存在真实网络时延**，
    因此本次数据**不能用于推断真实网络下的端到端时延**。
  - 拥塞控制为内核默认 `cubic`（本项目未做任何调整）。

### 4.3 资源稳定性

**(a) 基准运行期间（每场景约 100 s，1 s 采样）**

| 场景 | 采样数 | 时长 | VmRSS 首→末（kB） | 线程数 | fd 数 |
|---|---|---|---|---|---|
| idle/relative | 102 | 102.2 s | 1960 → 2348（+388） | 恒为 3 | 恒为 19 |
| traffic/relative | 101 | 101.2 s | 2004 → 2392（+388） | 恒为 3 | 恒为 19 |
| load/relative | 98 | 102.5 s | 2028 → 2416（+388） | 恒为 3 | 恒为 19 |
| traffic/absolute | 99 | 99.2 s | 2024 → 2408（+384） | 恒为 3 | 恒为 19 |

> **关于这 +388 kB 的精确解释**：四个基准场景都带了 `--benchmark --cycles 10000`，
> `metrics_init()` 会一次性 `calloc(10000, sizeof(CycleSample))`。
> `sizeof(CycleSample)` = 40 B（4×uint64 + 2×int32，8 字节对齐），
> 10000 × 40 B = 400000 B = **390.6 KiB**，与实测 +384~388 kB **完全吻合**。
> 也就是说这段增长是**刻意预分配的采样缓冲区**，而不是泄漏；
> 采样数组在运行期不再增长（`dropped=0` 已证明容量足够）。
> 下面的 30 分钟 soak **不带 `--benchmark`**，可用来交叉验证这一点。

**(b) 长期运行观测（30 分钟，5 s 采样）**

见 `results/03_resource_usage_soak.csv` 与 `logs/soak_run.log`。
采样项：`VmRSS`、线程数、`/proc/<pid>/fd` 计数、自愿/非自愿上下文切换。

命令 `bash performance_evaluation/scripts/run_soak.sh 1800 5`（持续 1800 s，每 5 s 一次，共 360 个采样点）：

| 观测项 | 首次采样（0.001 s） | 末次采样（1799.3 s = 29.99 min） | 全程 min / max | 变化量 |
|---|---|---|---|---|
| VmRSS (kB) | 2016 | **2016** | 2016 / 2016 | **0** |
| Threads | 3 | **3** | 3 / 3 | **0** |
| fd_count | 19 | **19** | 19 / 19 | **0** |
| voluntary_ctxt_switches | 1 | 1 | 1 / 1 | 0 |
| nonvoluntary_ctxt_switches | 0 | 0 | 0 / 0 | 0 |

同期服务端统计（`logs/soak_run.log`）：**推送状态帧 180456 帧，收到控制帧 177108 帧，
坏控制帧 0，seq 跳变 0**；结束时向进程发送 `SIGTERM`，进程**优雅退出**（退出码 0，
日志以 `Shutting down... / Goodbye.` 结束，无残留进程）。

> **交叉验证**：本次 soak **不带 `--benchmark`**，因此没有预分配采样数组，
> `VmRSS` 从第 5 秒到第 1800 秒**逐采样点恒定 2016 kB、变化量为 0**。
> 这与 4.3(a) 中基准场景的 +388 kB 完全互补，共同证明那 388 kB 就是
> `metrics_init()` 一次性预分配的采样缓冲区，而非运行期增长。
>
> **表述边界（不夸大）**：30 分钟、360 个采样点内**未观察到 RSS / 线程数 / fd 数增长**，
> 这是**观察结论**；要下"无内存泄漏"的结论仍需 Valgrind 全量 memcheck 或长时间
> ASan 插桩（本次 ASan 只覆盖协议解析路径，未对完整程序插桩）。

**结论与边界**：
- 线程数恒为 3（主 + 发送 + 接收），**未观察到线程泄漏**。
- fd 数恒为 19（stdio + socket + 日志等），**未观察到 fd 泄漏**。
- `VmRSS` 在启动后约 1 秒内由 ~2.0 MB 升至 ~2.4 MB（+388 kB，为 stdio 缓冲与首次
  写日志文件导致的堆分配），之后在**同一个值上持平，未再增长**。
- **明确边界**：以上是**有限时长内的观察结果**。要下"无内存泄漏"的结论，
  必须配合 Valgrind/ASan 的完整覆盖（本次 ASan 只覆盖协议解析测试路径，
  未对完整程序插桩）。因此报告中**不写"无内存泄漏"**，只写"未观察到单调增长"。
