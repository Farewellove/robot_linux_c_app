## 1. 项目概述

### 1.1 项目要解决的问题

**问题**：原"爬壁机器人焊接检测控制系统 v3.0"上位机基于 Qt5/C++ 开发，依赖 Qt Widgets、Qt Network、Qt SerialPort、OpenGL、OpenCV 4 等多个大型库。部署到嵌入式 ARM Linux 平台时，需要交叉编译整套依赖链，体积大、资源占用高、部署困难。

**解决方案**：用纯 C11 + POSIX API 重写上位机的 TCP 通信和协议解析核心功能，去除 GUI（OpenGL 3D 显示、摄像头预览），只保留命令行形式的机器人实时控制和数据记录功能，实现零外部依赖。

### 1.3 项目的输入、输出和最终实现效果

**输入**：
- 命令行参数（IP、端口、使能、模式、速度分量 Vx/Vy/Vz、发送周期、`--benchmark`、`--log-dir` 等）
- 通过 TCP socket 从对端接收的 20 字节二进制状态帧：
  `'u'` UWB 定位帧 / `'c'` 车体状态帧 / **`'i'` IMU 帧** / **`'a'` AP3216C 帧**
- 板端 `sensor_robot` 一侧的输入是真实传感器：`/sys/bus/iio/devices/iio:deviceN/*_raw`

**输出**：
- 通过 TCP socket 向对端发送的 20 字节二进制控制帧（周期发送）
- 控制台实时打印解析后的 UWB / 车体 / IMU / AP 数据
- `log/robot_linux_c_app/` 下时间戳命名的 CSV 日志（`robot_log_<时间>.csv`）
- `--benchmark` 时额外的逐周期指标 CSV（`03_periodic_timing.csv`）

**最终实现效果**：
- 编译出 3 个 ELF：`robot_linux_app`（上位机）、`mock_robot`（虚拟数据对端）、
  **`sensor_robot`（真实传感器对端）**
- 命令行运行，`Ctrl+C` 优雅退出（不会挂死）
- 默认以 10ms 周期（100Hz）发送控制帧
- 实时接收、解析、打印、记录对端回传的状态帧
- **已在 i.MX6ULL 开发板上实测**：真实 IMU 数据 2741 帧零丢帧、IMU 采样率 100.03 Hz

### 1.5 完整工作流程（一段话概括）

> 程序启动后解析命令行参数，通过 `getopt_long` 获取对端 IP、端口、控制模式、速度、日志目录等配置。使用 `socket()→inet_pton()→connect()` 建立 TCP 连接，设置 `TCP_NODELAY` 禁止 Nagle 算法、`SO_KEEPALIVE` 检测断线。打开 `log/robot_linux_c_app/robot_log_<时间>.csv`（目录递归创建，写 4 行表头）。创建两个 pthread 线程：sender_thread 以 `clock_nanosleep(CLOCK_MONOTONIC)` 定时周期性地构建 20 字节控制帧（帧头 0x77、使能/模式/速度、自增序列号、帧尾 0x0A）并通过 `send()` 发送（可选 `--abs-timer` 绝对时间模式与 `--benchmark` 指标采集）；receiver_thread 阻塞在 `recv()` 接收数据，喂入滑动窗口粘包状态机——逐字节缓冲 20 字节后校验帧尾魔数 0x55 0x56，合法则按帧头 `'u'` / `'c'` / `'i'` / `'a'` 分派解析为 UWB 定位帧、车体状态帧、IMU 帧或 AP3216C 帧（使用 memcpy 安全读取未对齐二进制字段），通过回调打印到控制台并写入 CSV 日志。SIGINT/SIGTERM 信号只置标志位，主线程在 `join(receiver)` 前先 `shutdown()` 唤醒阻塞的 recv，两线程退出后执行 goto cleanup 统一关闭 socket、日志文件和互斥锁。
>
> **对端有两个**：`mock_robot` 推虚拟数据（回归用），`sensor_robot` 读板载 ICM20608 / AP3216C 的
> IIO sysfs 推**真实数据**（`sensor_robot` 是单线程 `select()` 循环：一边按周期采样推帧，
> 一边接收并校验上位机下发的控制帧）。

### 5.2 TCP 粘包/半包处理：滑动窗口状态机

**这是本项目最核心的技术实现。**

**文件**：[src/robot_protocol.c:45-105](src/robot_protocol.c#L45-L105)
**函数**：`recv_buffer_feed()`
**数据结构**：`RecvBuffer`（[include/robot_protocol.h](include/robot_protocol.h)）

**算法原理**：

```
状态变量: rb->buf[20] (环形缓冲区), rb->wr (写指针, 0..20)
帧尾魔数: buf[18] == 0x55 && buf[19] == 0x56

每收到一批字节，逐个处理:
  for each byte in received_data:
    buf[wr++] = byte

    if wr == 20:  // 缓冲区满20字节
      if buf[18]==0x55 && buf[19]==0x56:
        ↓ 帧合法: 根据buf[0]分派解析（4 种帧类型）
        ├ buf[0]=='u' → parse_uwb_frame() → on_frame(UWB)
        ├ buf[0]=='c' → parse_car_frame() → on_frame(CAR)
        ├ buf[0]=='i' → parse_imu_frame() → on_frame(IMU)
        └ buf[0]=='a' → parse_ap_frame()  → on_frame(AP)
        wr = 0  ← 重置缓冲区

      else:
        ↓ 帧非法: memmove(buf, buf+1, 19)  ← 左移1字节
        wr = 19  ← 继续接收下一个字节
```

**设计要点**：
1. **不需要帧头魔数**：利用固定帧尾 `{0x55, 0x56}` 定位帧边界，无论上游数据如何错位
   （帧头不固定：`'u'`/`'c'`/`'i'`/`'a'` 四种，所以只能靠统一的帧尾同步）
2. **最坏情况恢复时间**：最多丢弃 19 个字节后即可重新同步（因为下 20 字节必然包含一个合法帧尾）
3. **`memmove` 而非 `memcpy`**：源 `buf+1` 和目标 `buf` 内存重叠，`memmove` 保证正确性
4. **处理范围**：可同时正确处理 TCP 粘包（多帧粘连）和 TCP 半包（帧不完整）
5. **新增帧类型零改动**：加 `'i'` / `'a'` 时只增加了两个分派分支，状态机与帧尾同步逻辑一行未动
   ——这是"用帧尾同步"带来的可扩展性，也是面试时值得讲的点
6. **已知边界**：帧尾合法但帧头不属于这四种时，该 20 字节被**静默丢弃**（用例 T08 固化此行为）

### 5.3 二进制协议的安全解析：`memcpy` 避免未对齐访问

**文件**：`parse_uwb_frame()`（[robot_protocol.c:140](src/robot_protocol.c#L140)）、
`parse_car_frame()`（[robot_protocol.c:168](src/robot_protocol.c#L168)）、
`parse_imu_frame()`（[robot_protocol.c:290](src/robot_protocol.c#L290)）、
`parse_ap_frame()`（[robot_protocol.c:308](src/robot_protocol.c#L308)）

**核心模式**（以 UWB 解析为例）：
```c
// [robot_protocol.c] parse_uwb_frame()
memcpy(&out->tag_num, buf + 2,  4);   // int32_t
memcpy(&out->x,       buf + 6,  4);   // float
memcpy(&out->y,       buf + 10, 4);   // float
memcpy(&out->z,       buf + 14, 4);   // float
```

**为什么要用 `memcpy` 而不是指针强转？**
- `buf` 是 `uint8_t*`，对齐为 1 字节
- `int32_t` 和 `float` 在 ARM 上要求 4 字节对齐
- 直接写 `*(int32_t*)(buf+2)` 在 ARM 上可能触发 **SIGBUS**（总线错误）
- `memcpy` 内部处理未对齐内存访问，编译器也会内联优化掉函数调用开销

**CAR 帧解析的缩放算法**（`parse_car_frame()`）：
```c
// 速度: int8 定点数 → 浮点
out->vx = (int8_t)buf[1] / 100.0f;   // 精度 0.01

// 角度变化: int16 定点数 → 浮点
int16_t d_angle_raw;
memcpy(&d_angle_raw, buf + 6, 2);
out->d_angle = d_angle_raw / 100.0f;

// 姿态角: int16 → 度 (180/32768 ≈ 0.0055°分辨率)
int16_t yaw_raw;
memcpy(&yaw_raw, buf + 12, 2);
out->yaw = yaw_raw / 32768.0f * 180.0f;
```

**IMU 帧：原始值上帧、物理量在解析侧换算**（`imu_raw_to_physical()`，[robot_protocol.c:216](src/robot_protocol.c#L216)）：
```c
// 线上只传 int16 原始值，换算系数以宏定义在 robot_protocol.h，收发两侧共用一份
out->accel_g[i]  = (float)raw[i]     / ICM_ACCEL_LSB_PER_G;    // 2048.0 → g
out->gyro_dps[i] = (float)raw[3 + i] / ICM_GYRO_LSB_PER_DPS;   // 16.4   → °/s
out->temp_c      = (float)raw[6]     / ICM_TEMP_LSB_PER_C + ICM_TEMP_OFFSET_C;  // 326.8 / +25 → ℃
```
这样做的两个理由：① int16 比 float 省一半带宽（20 字节装得下 7 个通道）；
② 换算系数只有一份定义，不会出现"板端算一遍、上位机再算一遍"的系数漂移。

### 5.4 TCP 可靠发送封装：循环 `send()`

**文件**：[src/robot_tcp.c:66](src/robot_tcp.c#L66)
**函数**：`tcp_send_all()`

```c
// [robot_tcp.c]
int tcp_send_all(int fd, const void *buf, size_t len)
{
    const char *ptr = (const char *)buf;
    size_t remaining = len;
    while (remaining > 0) {
        ssize_t n = send(fd, ptr, remaining, MSG_NOSIGNAL);
        if (n < 0) {
            if (errno == EINTR) continue;  // 被信号中断→重试
            perror("send");
            return -1;
        }
        if (n == 0) {  // 对端关闭写端
            fprintf(stderr, "send: connection closed by peer\n");
            return -1;
        }
        ptr      += n;
        remaining -= n;
    }
    return 0;
}
```

**三个必须处理的情况**：
1. `send()` 返回值 `< len`：TCP 发送缓冲区满，只发了部分数据 → 循环继续
2. `errno == EINTR`：系统调用被信号中断 → 不是错误，重试
3. `MSG_NOSIGNAL`：防止对端关闭时内核发送 SIGPIPE 杀死进程 → 改为通过返回值 `-1` + `EPIPE` 处理

### 5.5 精确周期定时：`clock_nanosleep(CLOCK_MONOTONIC)`

**文件**：[src/main.c:134-263](src/main.c#L134-L263)（`sender_thread`）

```c
// [main.c] 默认：相对睡眠（flag = 0）
struct timespec req;
req.tv_sec  = period_ns / 1000000000L;
req.tv_nsec = period_ns % 1000000000L;
clock_nanosleep(CLOCK_MONOTONIC, 0, &req, NULL);

// [main.c] --abs-timer：绝对时间定时（TIMER_ABSTIME），误差不累积
next_sched_ns += (uint64_t)period_ns;
target.tv_sec  = next_sched_ns / 1000000000ULL;
target.tv_nsec = next_sched_ns % 1000000000ULL;
clock_nanosleep(CLOCK_MONOTONIC, TIMER_ABSTIME, &target, NULL);
```

**设计要点**：
- **`CLOCK_MONOTONIC` 而非 `CLOCK_REALTIME`**：不受系统时间调整（NTP、手动）影响，保证周期稳定
- **`clock_nanosleep` 而非 `usleep`/`nanosleep`**：`usleep` 已被 POSIX 废弃，`clock_nanosleep` 支持指定时钟源，且支持绝对时间模式（TIMER_ABSTIME）避免累积误差
- **已知精度局限**：相对睡眠下实际周期 = 目标周期 + 本周期工作耗时，误差逐周期累积；
  `--abs-timer` 就是为了消除这种累积而加的（默认仍走相对睡眠，保证行为不变）
- **实测数字**（板端 i.MX6ULL，10ms 周期，4741 个样本）：周期偏差 mean 194.6 μs / p99 263 μs /
  max 489 μs，工作耗时（组帧+发送）mean 88.2 μs / p99 143 μs
- **不是硬实时**：未使用 `SCHED_FIFO`、未做 CPU 隔离、非 PREEMPT_RT 内核，上述抖动是普通 CFS 调度的正常量级

### 5.6 信号驱动的优雅关闭

**文件**：[src/main.c:40-53](src/main.c#L40-L53)（定义）、[main.c:402-404](src/main.c#L402-L404)（注册）

```c
// [main.c:40]
static volatile sig_atomic_t g_running = 1;

// [main.c:46]
static void signal_handler(int sig)
{
    (void)sig;
    g_running = 0;  // 只设置标志位，不执行任何复杂操作
}

// [main.c:402-404]
signal(SIGINT,  signal_handler);
signal(SIGTERM, signal_handler);
signal(SIGPIPE, SIG_IGN);
```

**一个真实缺陷及其修复**（值得在面试里讲）：信号由内核投递给"任意一个未屏蔽它的线程"。
若被 main 或 sender 收走，而对端此刻静默（不发数据也不断开），receiver 会一直阻塞在 `recv()`，
`pthread_join` 永久挂起，只能 `kill -9`（已实测复现）。
修复：在 `join(receiver)` 之前先 `shutdown(g_sockfd, SHUT_RDWR)`（[main.c:457](src/main.c#L457)），
内核会让阻塞中的 `recv` 立即返回 0。修复后 `SIGINT` 到退出耗时 0.102 s。

**三个信号的语义**：
| 信号 | 处理 | 原因 |
|------|------|------|
| SIGINT | 设置 g_running=0 | Ctrl+C → 优雅退出 |
| SIGTERM | 设置 g_running=0 | kill 默认信号 → 优雅退出 |
| SIGPIPE | SIG_IGN（忽略） | 写已关闭的 socket 时内核发此信号，默认杀死进程。配合 send() 的 MSG_NOSIGNAL 双重保险 |

**`volatile sig_atomic_t` 的意义**：
- `volatile`：防止编译器将变量缓存到寄存器，确保每次读取都从内存获取
- `sig_atomic_t`：保证读写是原子的（通常 typedef 为 `int`），信号处理函数和主循环不会看到中间状态
- 信号处理函数中只做赋值，不调用任何非异步信号安全的函数（如 `printf`、`malloc`、`pthread_mutex_lock`）

### 5.7 Tagged Union（标记联合体）实现多态

**文件**：[include/robot_protocol.h](include/robot_protocol.h)

```c
typedef enum {
    FRAME_TYPE_NONE = 0,
    FRAME_TYPE_UWB,     // = 1
    FRAME_TYPE_CAR,     // = 2
    FRAME_TYPE_IMU,     // = 3  （2026-10-13 新增：ICM20608）
    FRAME_TYPE_AP,      // = 4  （2026-10-13 新增：AP3216C）
} FrameType;

typedef struct {
    FrameType type;       // ← 标记(tag)
    union {
        UwbState   uwb;  // type==FRAME_TYPE_UWB 时有效
        RobotState car;  // type==FRAME_TYPE_CAR 时有效
        ImuState   imu;  // type==FRAME_TYPE_IMU 时有效
        ApState    ap;   // type==FRAME_TYPE_AP  时有效
    } data;

```

**使用模式**（[main.c:57-128](src/main.c#L57-L128) `on_parsed_frame`）：
```c
switch (frame->type) {
case FRAME_TYPE_UWB: /* 安全访问 frame->data.uwb */ break;
case FRAME_TYPE_CAR: /* 安全访问 frame->data.car */ break;
case FRAME_TYPE_IMU: /* 安全访问 frame->data.imu */ break;
case FRAME_TYPE_AP:  /* 安全访问 frame->data.ap  */ break;
```

**为什么用 tagged union**：4 种帧长度都是 20 字节但字段布局完全不同，

### 5.9 真实传感器读取：IIO sysfs + 常驻 fd + `pread`

**文件**：[src/iio_util.c](src/iio_util.c)、[src/icm20608.c](src/icm20608.c)、[src/ap3216c.c](src/ap3216c.c)

```c
/* 1) 设备号取决于驱动加载顺序，必须按 name 匹配，不能写死 iio:deviceN */

/* 2) open 一次，之后每次采样只 pread —— sysfs 在 pos==0 时会重新执行 show()，即重新采样 */

```

**三个值得讲的点**：
1. **为什么不写死 `iio:device1`**：实测时 `iio:device1` 是 ICM20608、`iio:device0` 是 AP3216C，
   编号由加载顺序决定，写死就会取错设备；
2. **为什么用 `pread` 而不是每次 `open`/`read`/`close`**：每帧要读 7 个属性，
   常驻 fd 后系统调用从 21 次降到 7 次；
3. **为什么是用户态轮询而不是中断**：这是 IIO sysfs 接口的固有形态（无 trigger/buffer 时），

   **面试时必须说清它不是硬实时采样**。

**代价与边界**：读取失败时计数并**跳过该帧**，不发全零帧污染数据；
`int → int16` 饱和截断，不静默回绕；驱动未加载时等待 `--wait` 秒后以退出码 3 退出。

#### 并发场景时序分析

```
时间轴 →

信号处理函数:        g_running = 0  (任意时刻)
sender_thread:   send() send() send() ... [g_running==0] 退出
receiver_thread: recv() recv() recv() ... [g_running==0] 退出
main:             pthread_join(sender) → pthread_join(receiver) → cleanup
```

**退出时序保证**：
1. 信号到来 → `g_running = 0`
2. sender 可能在 `send()` 阻塞或在 `clock_nanosleep` 睡眠中 → 下次循环条件检查时退出
3. receiver 可能在 `recv()` 阻塞中 → **已修复**：main 在 `join(receiver)` 之前先
   `shutdown(g_sockfd, SHUT_RDWR)`（[main.c:457](src/main.c#L457)），内核让阻塞的 `recv` 立即返回 0。
   修复前：对端静默时 receiver 永久阻塞，`pthread_join` 挂死，只能 `kill -9`（已实测复现）；
   修复后：SIGINT 到退出 0.102 s
4. main 依次 `join(sender)` → `shutdown` → `join(receiver)` → cleanup

### 6.2 内存管理分析

#### 内存分配/释放清单

| 分配点 | 文件 | 分配方式 | 释放点 | 释放方式 | 风险 |
|--------|------|----------|--------|----------|------|
| `g_log_fp` | [src/logger.c](src/logger.c) | `fopen(path, "w")` | [main.c:466](src/main.c#L466) cleanup | `fclose(fp)` | ✅ |
| `g_sockfd` | [src/robot_tcp.c](src/robot_tcp.c) | `socket()` | cleanup → `tcp_close()` | `shutdown()+close()` | ✅ |
| `Metrics` 采样数组 | [src/metrics.c](src/metrics.c) | `malloc`（**仅 `--benchmark` 时**） | `metrics_free()`（发送线程退出前） | `free()` | ✅ |
| 传感器属性 fd | [src/iio_util.c](src/iio_util.c) | `open()`（板端 `sensor_robot`） | `icm20608_close()` / `ap3216c_close()` | `close()` | ✅ |
| sender/receiver 线程栈 | [src/main.c](src/main.c) | 自动（线程栈） | 线程退出时 | 自动回收 | ✅ |

**内存使用风格**：默认路径**全部栈分配**，无 `malloc`/`free`（除 `fopen` 内部）。
唯一的堆分配是 `--benchmark` 时预分配的指标采样数组，且已在同线程内 `free`；
默认关闭时**不分配、不打点**，这也是"默认行为不变"的体现。

#### 潜在风险分析

| 风险类型 | 位置 | 严重程度 | 说明 |
|----------|------|----------|------|
| **receiver 阻塞无法退出** | [main.c:457](src/main.c#L457) | **已修复** | 原为"对端静默时 recv 永久阻塞、只能 kill -9"；现在 join 前先 `shutdown()` 唤醒 |

| **传感器读取失败**（板端） | [tests/sensor_robot.c](tests/sensor_robot.c) | 低 | 计数并跳过该帧，不发全零帧；连续失败可从 `--csv` 统计里的 `err_imu_read/err_ap_read` 看出 |

### 7.1 从代码中可确认的工程决策

| 决策 | 代码证据 | 推断原因 |
|------|----------|----------|
| 用 `MSG_NOSIGNAL` + `SIG_IGN` 双重防 SIGPIPE | [src/robot_tcp.c](src/robot_tcp.c)、[main.c:404](src/main.c#L404) | 对端关闭时 `send` 否则触发 SIGPIPE 杀死进程 |

| 用**帧尾**而非帧头同步 | `is_valid_status_frame` | 帧头有 `'u'/'c'/'i'/'a'` 四种不固定，帧尾统一；后来加帧类型时状态机一行没改，验证了取舍正确 |

| 传感器只传 int16 原始值 | `imu_raw_to_physical` | 省带宽 + 换算系数只有一份定义，避免两处漂移 |

#### 版本 B：详细版（适合"项目经历"展开描述）

> **机器人控制 Linux C 上位机**（原 Qt/C++ 版本的重写）
>
> **背景**：原爬壁机器人焊接检测控制系统上位机基于 Qt5 + OpenCV + OpenGL 开发，依赖复杂、体积大、不适合嵌入式 ARM 平台部署。
>
> **我的工作**：用纯 C11 + POSIX API 完整重写核心通信功能，去除所有第三方依赖，保留完整的 TCP 协议交互和数据分析能力。
>
> **核心技术实现**：
> 1. **TCP 粘包状态机**：基于帧尾魔数（0x55 0x56）+ 滑动窗口的字节级状态机，逐字节缓冲 20 字节后校验帧尾，合法则按 `buf[0]` 分派解析，否则 `memmove` 左移 1 字节重新同步。因为帧头有 4 种不固定，用统一帧尾做边界，后来新增 IMU / 环境光两种帧时状态机一行未改。
> 2. **双线程并发架构**：pthread 发送线程用 `clock_nanosleep(CLOCK_MONOTONIC)` 做 100Hz 周期发送（可选 `TIMER_ABSTIME` 绝对定时消除累积误差），接收线程阻塞 recv 后喂入状态机；`volatile sig_atomic_t` + SIGINT/SIGTERM 安全退出。
> 3. **安全二进制解析**：统一 `memcpy` 读取多字节字段（int32/float/int16），避免 ARM 未对齐访问触发 SIGBUS。
> 4. **真实传感器接入**：用户态读 IIO sysfs（`/sys/bus/iio/devices/iio:deviceN/*_raw`）——按 `name` 定位设备（编号会变，不能写死）、属性 fd 常驻 + `pread` 复用（每帧系统调用 21→7 次）；线上只传 int16 原始值，换算系数收发共用一份宏定义。
> 5. **CSV 实时日志与产物治理**：`clock_gettime(CLOCK_REALTIME)` 微秒级时间戳、逐帧 `fflush`；所有运行期产物统一落在 `log/<项目名>/`，不污染板端共用目录。
>
> **结果**：可执行文件无外部依赖；交叉编译部署到 i.MX6ULL（ARMv7，Linux 4.1.15）实测通过 ——
> 10ms 周期偏差 mean 194.6 μs / p99 263 μs；真实传感器数据链路 2741 帧零丢帧、100.03 Hz；
> 协议解析 19 类自动化用例 + ASan/UBSan 全通过。

<summary><b>Q1-Q5：C 语言基础</b></summary>

**Q1：`memmove` 和 `memcpy` 的区别是什么？项目中哪里用到了？为什么必须用 `memmove`？**

> **参考答案**：`memcpy` 假设源和目标内存不重叠，`memmove` 处理重叠情况（内部判断复制方向）。项目中在 [src/robot_protocol.c:84](src/robot_protocol.c#L43) 使用 `memmove(rb->buf, rb->buf + 1, 19)`，因为 `buf` 和 `buf+1` 是重叠内存区域。如果用 `memcpy`，行为未定义，可能数据损坏。

**Q2：`volatile` 关键字的作用？项目中为什么 `g_running` 要加 `volatile`？**

> **参考答案**：`volatile` 告诉编译器不要优化该变量的读写（不要缓存到寄存器、不要重排）。[main.c:40](src/main.c#L16) 中 `g_running` 被信号处理函数和主循环/线程共享，如果不加 `volatile`，编译器可能将 while(g_running) 优化为读取一次寄存器值后无限循环，导致信号无法终止程序。

**Q3：C 语言中 `union` 的作用？项目中是如何使用 `union` 的？**

> **参考答案**：[include/robot_protocol.h:42-45](include/robot_protocol.h#L42-L45) 中 `ParsedFrame.data` 是 union，包含 `UwbState` 和 `RobotState`。配合 `FrameType type` 形成 Tagged Union（标记联合体）模式，根据 `type` 决定访问哪个成员。优点是节省内存，缺点是开发者必须自行保证类型安全——访问错误的 union 成员是未定义行为。

**Q4：`pthread_mutex_t` 的静态初始化器 `PTHREAD_MUTEX_INITIALIZER` 是什么？和 `pthread_mutex_init` 有什么区别？**

> **参考答案**：[main.c:43](src/main.c#L19) 使用 `PTHREAD_MUTEX_INITIALIZER` 静态初始化。这只适用于静态分配的互斥锁，在编译期完成，不需要在运行时调用 init，也不需要配对 destroy（但项目仍然调用了 [main.c:475](src/main.c#L255) 的 destroy）。相比之下 `pthread_mutex_init` 用于动态分配的互斥锁。

**Q5：为什么需要在 `recv()` 和 `send()` 中处理 `EINTR`？**

> **参考答案**：当进程收到信号时，正在执行的慢速系统调用（如 `recv`、`send`）可能被中断，返回 -1 且 errno=EINTR。这不是真正错误，应该重试。[robot_tcp.c:74](src/robot_tcp.c#L51) 和 [robot_tcp.c:100](src/robot_tcp.c#L69) 做了这个处理。注意项目使用了 `MSG_NOSIGNAL` 避免 SIGPIPE，且没有设置 SA_RESTART，所以 EINTR 处理是必要的。

<details>
<summary><b>Q6-Q10：网络编程</b></summary>

**Q6：TCP 三次握手在代码中哪里完成？四次挥手在哪里完成？**

> **参考答案**：三次握手在 [robot_tcp.c:46](src/robot_tcp.c#L31) `connect()` 调用时由内核完成（SYN→SYN-ACK→ACK）。四次挥手在 [robot_tcp.c:141](src/robot_tcp.c#L95) `shutdown(fd, SHUT_RDWR)` 发送 FIN 开始，[robot_tcp.c:142](src/robot_tcp.c#L96) `close(fd)` 释放资源。

**Q7：为什么要设置 `TCP_NODELAY`？不设置会怎样？**

> **参考答案**：[robot_tcp.c:257-121](src/robot_tcp.c#L80-L84) `tcp_set_no_delay()` 通过 `setsockopt(TCP_NODELAY)` 禁用 Nagle 算法。Nagle 算法会缓冲小包等待 ACK 或积累到 MSS 再发送，对 100Hz（10ms）的实时控制来说，可能导致额外 40ms 延迟。禁用后每次 `send()` 立即发送。

**Q8：`tcp_send_all` 为什么需要循环 `send()`？一次 `send()` 不能保证发送完吗？**

> **参考答案**：[robot_tcp.c:66-86](src/robot_tcp.c#L43-L63)。TCP 是流式协议，`send()` 将数据拷贝到内核发送缓冲区，返回值是实际拷贝的字节数。如果缓冲区空间不足（如接收方通告窗口太小），只能部分拷贝。因此必须循环直到全部数据发送完毕。

**Q9：`shutdown` 和 `close` 的区别？**

> **参考答案**：[robot_tcp.c:138-143](src/robot_tcp.c#L92-L96) 中 `tcp_close` 先 `shutdown(fd, SHUT_RDWR)` 再 `close(fd)`。`shutdown` 发送 FIN 通知对端断开（TCP 层面），但 fd 仍然可用（可以接收对端残余数据）；`close` 释放 fd（文件描述符层面）。如果其他进程通过 `fork`/`dup` 共享了同一个 socket fd，`close` 不会真正关闭（引用计数），而 `shutdown` 会。项目中先 shutdown 再 close 是最安全的做法。

**Q10：`MSG_NOSIGNAL` 标志的作用？如果没有它会怎样？**

> **参考答案**：[robot_tcp.c:72](src/robot_tcp.c#L49)。当向一个已经关闭的连接 `send()` 时，内核会向进程发送 `SIGPIPE` 信号，默认行为是终止进程。`MSG_NOSIGNAL` 抑制信号的产生，改为通过 `send()` 返回 -1 且 errno=EPIPE 来通知程序。这样可以由程序自行决定如何处理，而不是被杀死。项目中还额外设置了 [main.c:404](src/main.c#L210) `signal(SIGPIPE, SIG_IGN)` 作为双重保险。
</details>

<details>
<summary><b>Q11-Q15：多线程与系统编程</b></summary>

**Q11：为什么要用两个线程而不是单线程？单线程怎么做？**

> **参考答案**：分离发送和接收是为了解耦精确定时和阻塞 IO。单线程方案可以用 `select`/`poll`/`epoll` + 非阻塞 socket：设置超时等于下次发送时间，超时后发送控制帧，有数据时接收。双线程方案代码逻辑更清晰，但多了一个线程的栈开销（约 8MB 虚存）。选择双线程是因为发送的精确周期（clock_nanosleep）和接收的阻塞（recv）互不干扰。

**Q12：`clock_nanosleep(CLOCK_MONOTONIC, ...)` 和 `usleep` 有什么区别？**

> **参考答案**：[main.c:256-260](src/main.c#L99-L102)。`usleep` 已被 POSIX 废弃，且精度只到微秒。`clock_nanosleep` 精度到纳秒，且第一个参数指定时钟源：`CLOCK_MONOTONIC` 不受系统时间调整（NTP/手动）影响，保证周期性任务的间隔稳定；`CLOCK_REALTIME` 会因校时跳变。项目中发送线程使用 `CLOCK_MONOTONIC`，日志时间戳使用 `CLOCK_REALTIME`（[logger.c:81](src/logger.c#L81)），各自选择了正确的时钟源。

**Q13：信号处理函数中为什么只能设置一个标志位？可以在里面打印日志吗？**

> **参考答案**：[main.c:46-24](src/main.c#L21-L24)。信号处理函数异步执行，可能打断任意代码（包括持有锁的代码）。`printf` 内部使用 `malloc` 和锁，如果在 malloc 持锁时被信号中断，信号处理函数中再次调用 `printf` 会导致死锁。POSIX 列出了有限的"异步信号安全"函数（见 `man 7 signal-safety`），包括 `write`、`_exit` 等。设置 `volatile sig_atomic_t` 标志位是最安全的做法。

**Q14：如果 CPU 是单核的，两个线程如何同时运行？**

> **参考答案**：Linux 使用时间片轮转调度（CFS 调度器），即使单核也能通过抢占式调度让两线程交替运行。receiver 大部分时间阻塞在 `recv()` 中（让出 CPU），sender 每 10ms 醒来发一次数据然后 sleep（也让出 CPU）。实际 CPU 占用非常低。

**Q15：`PTHREAD_MUTEX_INITIALIZER` 和 `pthread_mutex_init` 初始化的 mutex 在行为上有差异吗？**

> **参考答案**：`PTHREAD_MUTEX_INITIALIZER` 创建的是默认属性的 mutex（普通类型，不检查死锁，不记录 owner）。`pthread_mutex_init` 可以通过 `pthread_mutexattr_t` 创建不同属性的 mutex（如 `PTHREAD_MUTEX_ERRORCHECK` 会在同一线程重复加锁时返回错误而不是死锁）。项目中使用的默认属性足够满足需求。

**Q41：现象：程序启动后连接成功，但没有任何数据打印，也不报错。如何排查？**

> **排查思路**：
> 1. 检查是否 `enable=0`：发送的控制帧 enable 字段为 0，机器人可能不回复。尝试 `./robot_linux_app -e 1`
> 2. 检查模式是否正确：mode=0(STOP) 时机器人可能不运动但仍应回复状态。尝试 `-m 1`
> 3. 用 `tcpdump -i any port 9090 -X` 抓包，确认是否有双向数据流
> 4. 用 `strace -p $(pidof robot_linux_app)` 观察 recv 是否阻塞、有无数据返回
> 5. 用 `nc -l 9090` 替代机器人监听，手动发送 `echo -ne 'upp....' | nc ...` 测试解析是否正常

**Q42：现象：程序随机崩溃，没有打印任何错误信息。可能的原因？**

> **排查思路**：
> 1. 最可能原因：SIGPIPE。检查是否正确设置了 `MSG_NOSIGNAL` 和 `signal(SIGPIPE, SIG_IGN)`。代码中两者都有 [robot_tcp.c:72](src/robot_tcp.c#L49) + [main.c:404](src/main.c#L210)，但如果是老版本代码可能只做了其一
> 2. 次可能原因：信号处理函数中调用了非异步信号安全的函数。检查 signal_handler 是否只设置了标志位——项目代码中确认只做了 `g_running = 0` [main.c:46](src/main.c#L23)，安全
> 3. `coredumpctl list` 查看是否有 core dump，用 gdb 分析崩溃位置
> 4. 用 `valgrind ./robot_linux_app ...` 检查内存问题

**Q43：现象：交叉编译到 ARM 板后，程序启动直接 SIGBUS 崩溃。原因和解决方案？**

> **排查思路**：
> 1. 最可能原因：未对齐内存访问。ARM 要求 int32/float 4 字节对齐，如果代码中使用了 `*(int32_t*)(buf+2)` 这种强转，buf+2 不是 4 的倍数会触发 SIGBUS
> 2. 检查项目代码：已使用 `memcpy` [robot_protocol.c:145-149](src/robot_protocol.c#L78-L81) 避免此问题，但如果某个版本用了强转就会出现
> 3. 解决方案：将所有 `*(type*)(buf+offset)` 改为 `memcpy(&var, buf+offset, sizeof(type))`
> 4. 用 `-Wcast-align` 编译选项可以让编译器对潜在的对齐问题发出警告

**Q44：现象：日志文件中有部分帧丢失，但控制台打印正常。可能原因？**

> **排查思路**：
> 1. fprintf 日志时 `fflush` 后紧接着 mutex_unlock [main.c:72](src/main.c#L72)。如果 flush 返回错误（如磁盘满），当前代码未检查 fprintf 返回值
> 2. 检查 `logger_write_car/uwb` 中 fprintf 的返回值——代码中确实未检查
> 3. 用 `df -h` 检查磁盘空间，`iostat -x 1` 检查磁盘 IO
> 4. 如果磁盘 IO 慢，多个 fflush 可能排队

**Q45：现象：程序运行一段时间后 CPU 占用 100%。如何定位？**

> **排查思路**：
> 1. `top -H -p $(pidof robot_linux_app)` 查看是哪个线程 CPU 高
> 2. 如果是 sender_thread：检查 send_period 是否是 0 或极小值。代码中 send_period_ms < 1 会报错 [main.c:386-388](src/main.c#L201-L203)，但如果用 1ms 周期且 clock_nanosleep 返回后立即循环，可能接近 100% CPU
> 3. 如果是 receiver_thread：检查 recv 是否返回了大量数据。代码中 `recv_buffer_feed` 逐字节处理，数据量大时会 CPU 密集
> 4. `perf top -p $(pidof robot_linux_app)` 查看热点函数
> 5. `strace -p $(pidof robot_linux_app) -c` 统计系统调用频率

**Q46：现象：Ctrl+C 后程序不退出，必须 kill -9。原因和解决方案？**

> **排查思路**：
> 1. 最可能原因：`recv()` 阻塞中无法响应 g_running 变化。[main.c:291](src/main.c#L120) 的 recv 是阻塞调用，只有收到数据或连接断开才会返回
> 2. 如果机器人停止发送数据且保持连接，receiver 永远阻塞在 recv，pthread_join 也永远等待
> 3. 解决方案（代码层面）：设置 socket 接收超时 `setsockopt(fd, SOL_SOCKET, SO_RCVTIMEO, &tv, sizeof(tv))`，超时后 recv 返回 -1 且 errno=EAGAIN，线程可以检查 g_running
> 4. 另一个方案：信号处理函数中直接 `close(g_sockfd)` 强制唤醒 recv（但这不是异步信号安全的操作）
> 5. 或者使用 `pthread_cancel` + cleanup handler —— 但这在 C 项目中有风险

**Q47：现象：CSV 文件中出现乱码或字段错位。可能原因？**

> **排查思路**：
> 1. 日志文件是文本模式（"w"）打开 [logger.c:91](src/logger.c#L37)，数据中如有 `\n` 会破坏 CSV 行结构。检查数值中是否有异常大的浮点数（如 NaN、Inf）
> 2. 如果程序被并发运行多个实例（未做单实例锁），两个进程写同一文件会导致交错
> 3. 文件名使用 `localtime_r` 生成，如果两个实例在同一秒启动，会写同一文件
> 4. printf 和 logger_write 都在同一个 mutex 保护下 [main.c:57-128](src/main.c#L31-L72)，并发写文件本身是安全的

**Q48：现象：`tcp_send_all` 返回 -1，但 socket 看起来正常。怎么定位？**

> **排查思路**：
> 1. 检查 errno：[robot_tcp.c:52](src/robot_tcp.c#L52) 有 perror
> 2. EPIPE：对端已关闭连接（即使本地觉得正常，可能是半开连接）
> 3. ECONNRESET：对端发送了 RST
> 4. EAGAIN/EWOULDBLOCK：发送缓冲区满（如果设置了非阻塞模式，本项目中未设置）
> 5. `ss -tnp | grep 9090` 查看 TCP 连接状态
> 6. `tcpdump` 抓包查看最后一次交互是 FIN 还是 RST

**Q49：现象：接收到的 UWB 坐标数据全是 0 或异常大/小的浮点数。可能原因？**

> **排查思路**：
> 1. 字节序不匹配：机器人发送大端序但上位机按小端解析。检查 [robot_protocol.c:145-149](src/robot_protocol.c#L78-L81) 使用 memcpy 直接拷贝，如果两端字节序不同需加 `ntohl` 转换
> 2. 帧边界错位：如果粘包状态机误判了一帧，后续所有帧都错位。检查设备端发送的帧尾是否确实是 0x55 0x56
> 3. 浮点格式不一致：确认机器人发送的是 IEEE 754 float32 而非其他格式

**Q50：现象：程序运行 100 小时后日志文件特别大。如何优化？**

> **排查思路**：
> 1. 估算：每条 UWB 日志约 50 字节 + CAR 约 80 字节，每秒约 100 条（假设 50+50 混合），每小时约 36MB，100 小时约 3.6GB——取决于 ext4 文件系统限制
> 2. 当前代码每次 fflush [logger.c:60,70](src/logger.c#L60-L70)，磁盘 IO 频繁但数据安全
> 3. 优化方案：定时切换日志文件（每天一个）、日志轮转（保留最近 N 个）、写入压缩（管道到 gzip）、只记录变化的数据（减少重复记录）

**Q61：你说接了真实传感器，那 ICM20608 的驱动是你写的吗？**

> **不是**。驱动是板端既有的 `icm20608.ko`（IIO 驱动，SPI 总线）。我在用户态读它导出的 sysfs 属性
> `/sys/bus/iio/devices/iio:deviceN/in_accel{0,1,2}_raw`、`in_anglvel{0,1,2}_raw`、`in_temp0_raw`。
> 本项目没有写、没有改、没有编译任何内核代码。AP3216C 同理（`ap3216c.ko`，I2C）。

**Q62：为什么不写死 `iio:device1`？**

> 设备号由驱动加载顺序决定，实测时 `iio:device1` 是 ICM20608、`iio:device0` 是 AP3216C——
> 换一次加载顺序就会取错设备。所以 `iio_find_device()` 遍历 `iio:device0..31`，
> 逐个读 `name` 文件，内容等于 `"icm20608"` / `"ap3216c"` 才算命中。

**Q63：每帧要读 7 个属性文件，开销怎么控制？**

> 属性 fd 在初始化时 `open` 一次并常驻，采样时用 `pread(fd, buf, n, 0)` 重读——
> sysfs 在 pos=0 时会重新执行 `show()`，即触发一次新的硬件采样。
> 这样每帧系统调用从 21 次（7×open/read/close）降到 7 次 `read`。
> 另外 `sensor_robot` 用 `--ap-every` 让 AP3216C 每 10 个周期才采一次，进一步降低开销。

**Q64：IMU 帧为什么不直接传 float 物理量？**

> 20 字节放不下 7 个 float（28 字节）；7 个 int16 只要 14 字节，加帧类型、seq、帧尾正好放下。
> 换算放在解析侧做，系数（`2048.0` / `16.4` / `326.8`+`25`）以宏定义在 `robot_protocol.h`，
> 收发两侧共用一份，不会出现"板端算一遍、上位机再算一遍"的系数漂移。

**Q65：真实传感器这条链路实测结果如何？能说它是硬实时采样吗？**

> 实测 27.4 秒：板端发 IMU 2741 帧 / AP 274 帧，PC 一条不差地收到；下行控制帧 2699 帧坏帧 0、seq 跳变 0；
> 采样率 IMU 100.03 Hz、AP 10.04 Hz；周期 p50 9.999 / p99 10.375 ms，最坏 46.838 ms（2740 个间隔里仅 1 次 >12 ms）。
> **不能说硬实时**：采样由用户态 `clock_nanosleep` + sysfs 读驱动，不是传感器数据就绪中断；
> 要做确定性采样得在驱动侧用中断/FIFO + 定时器触发，再配合 `SCHED_FIFO`。

### 10.5 方案改进题（10 道）

<details>
<summary><b>展开查看全部 10 题</b></summary>

**Q51：如果要支持多种机器人协议（不同帧格式），如何设计代码架构？**

> **参考答案**：将帧解析抽象为接口。定义 `FrameParser` 结构体包含函数指针 `int (*try_parse)(const uint8_t *buf, size_t len, ParsedFrame *out)` 和 `size_t frame_len`。维护一个解析器数组 `static FrameParser parsers[]`，`recv_buffer_feed` 中遍历解析器尝试解析。如果协议帧长不同，将 `STATUS_FRAME_LEN` 改为从解析器获取。

**Q52：如何加入自动重连功能？**

> **参考答案**：设计连接状态机：DISCONNECTED → CONNECTING → CONNECTED。receiver 检测到断线后不退出线程，而是设置状态为 DISCONNECTED，启动重连定时器（指数退避：1s, 2s, 4s, ..., max 30s）。主循环中 `while(g_running)` 内部检查状态，DISCONNECTED 时尝试重连。重连成功恢复 CONNECTED 状态，重置退避计数器。需要注意重连时的资源管理：先 close 旧 fd，再创建新的。

**Q53：如果要同时连接多个机器人，代码怎么改？**

> **参考答案**：将全局的 `g_sockfd` 改为连接数组。使用 `epoll` 替代每个连接一个接收线程——创建 epoll fd，将所有机器人 socket 加入，统一等待事件。sender 部分可以是一个线程轮询多个连接，也可以每个连接一个 sender 线程。关键是将 `AppConfig` 从单例改为多实例，每个连接维护自己的配置、序列号、接收缓冲区。

**Q54：如何提高 1ms 发送周期的精度？**

> **参考答案**：
> - 使用 `clock_nanosleep` 的 TIMER_ABSTIME 模式（绝对时间），避免累积误差：记录 `clock_gettime(CLOCK_MONOTONIC)` 作为下次发送的绝对时间
> - 如果 Linux 内核非实时（标准 CFS），给内核打 PREEMPT_RT 补丁
> - 将 sender 线程调度策略改为 `SCHED_FIFO`，优先级设高：`pthread_setschedparam`
> - 如果精度要求极高（微秒级），使用忙等待（polling）替代 sleep：`while(clock_gettime() < target) ;` 但 CPU 占用 100%
> - 使用硬件定时器（如果平台支持，如 /dev/rtc）

**Q55：如果要通过串口（UART）而不是 TCP 通信，需要改哪些地方？**

> **参考答案**：实现 `uart_connect/open/close`、`uart_send`、`uart_recv` 模块替代 `robot_tcp.c`。涉及：
> - 打开串口设备：`open("/dev/ttyUSB0", O_RDWR | O_NOCTTY)`
> - 配置 termios：波特率、数据位、停止位、校验位、`cfsetispeed/cfsetospeed`
> - 关闭 canonical 模式（原始二进制传输）、禁用 echo
> - 帧解析部分（`recv_buffer_feed`）完全复用，因为同样是流式传输，粘包问题仍然存在
> - 周期发送部分（`sender_thread`）完全复用

**Q56：如何加入 CRC 校验提高协议可靠性？**

> **参考答案**：修改控制帧和状态帧格式，在帧尾魔数前加入 CRC 字段（如 CRC-8 或 CRC-16）。例如将 `buf[16..17]` 改为 CRC-16，帧长可能从 20 扩展到 22 或保持 20 但压缩其他字段。`recv_buffer_feed` 的 `is_valid_status_frame` 中增加 CRC 计算和比较。CRC 算法选择：对于 20 字节短帧，CRC-8（1 字节）足够检测单比特错误，CRC-16 可以检测突发错误。

**Q57：如何支持运行时动态调整参数（如速度、模式）而不重启程序？**

> **参考答案**：几种方案：
> - Unix domain socket：创建 `/tmp/robot_control.sock`，`select`/`epoll` 监听（需要第三个线程或改造 receiver 线程为 epoll 循环），接收 JSON 命令
> - stdin 命令：用 `select` 监听 stdin，在主线程或单独线程中处理
> - 信号：用 SIGUSR1/SIGUSR2 触发预定义的动作（但只能发信号不能传参数）
> - 共享内存 + atomic 变量：另写一个配置工具写入共享内存，主程序定期读取（需要同步）
>
> 推荐方案是 Unix domain socket + 简单的文本协议（如 `mode=1\n`），改造成本最低。

**Q58：如果需要每秒处理 10000 帧（10KHz），当前架构的瓶颈在哪里？如何优化？**

> **参考答案**：
> 瓶颈分析：
> - `recv_buffer_feed` 逐字节循环：每帧 20 次迭代，10KHz = 200K 次循环/秒，CPU 可承受
> - `memmove` 在帧边界错位时调用：正常运行时不应频繁调用
> - `printf` 控制台输出：每帧 1 次 printf 是最大瓶颈。改为批量输出或只输出统计信息
> - `fflush` 每帧刷盘：改为定时刷盘（如每秒一次）
> - `clock_nanosleep` 精度：10KHz = 100μs 周期，已接近 `clock_nanosleep` 的精度极限
> - TCP 栈：考虑使用零拷贝（`sendfile`/`splice`）或 DPDK 旁路内核
>
> 优化方向：批量接收（增大缓冲区）、批量发送（攒帧一起发）、减少 printf/fflush 频率、使用环形缓冲区替代 memmove。

**Q59：如果要为这个项目写单元测试，你会怎么设计？测试哪些函数？**

> **参考答案**：
> - 可独立测试的函数（无外部依赖）：`build_control_frame`（给定参数验证输出字节）、`parse_uwb_frame`/`parse_car_frame`（构造已知字节序列验证解析结果）、`is_valid_status_frame`（合法/非法帧尾）、`mode_name`
> - 需要 mock 的函数：`tcp_send_all`、`tcp_recv_some`（mock socket）、`logger_open/write/close`（mock FS）
> - 关键测试用例：
>   - 粘包：一次喂入 40 字节（两帧粘连），验证解析出两帧
>   - 半包：先喂入 10 字节，再喂入 10 字节，验证正常解析

## 11. 一分钟项目介绍

### 11.1 30 秒版本（电梯演讲）

> 我做的是一个**机器人 TCP 实时控制上位机**。原版本用 Qt/C++ 写的，依赖很多库，在嵌入式 ARM 板上部署困难。我用纯 C11 + POSIX 从零重写，零第三方依赖。核心三件事：一是 TCP 粘包处理的状态机（用帧尾魔数识别 20 字节定长帧边界，支持 4 种帧类型）；二是双线程架构（一个线程 `clock_nanosleep` 做 100Hz 周期发送，另一个阻塞接收并解析回传数据）；三是**接了板上的真实传感器**——用户态读 ICM20608 六轴和 AP3216C 的 IIO sysfs，组包成 20 字节帧上传。已经在 i.MX6ULL 开发板上实测：10ms 周期偏差 p99 263 微秒，真实 IMU 数据 2741 帧零丢帧。

### 11.2 1 分钟版本（面试标准版）

> 这个项目是**爬壁机器人焊接检测控制系统的 Linux C 上位机**，背景是原 Qt/C++ 版本依赖 Qt5、OpenCV、OpenGL 等多个大型库，不适合嵌入式 ARM 平台部署。我的目标是用纯 C 重写核心通信功能，去掉所有第三方依赖。
>
> 项目目前 `src/` 下 9 个 `.c`、`include/` 下 8 个 `.h`、`tests/` 下 3 个 `.c`，源码约 2200 行，
> 用 C11 + POSIX 实现。**核心有四个技术点**：
>
> 第一，**TCP 粘包处理**。基于帧尾魔数的滑动窗口状态机——逐字节缓冲到 20 字节后检查帧尾 0x55 0x56，
> 合法就按 `buf[0]` 分派解析（UWB / 车体状态 / IMU / 环境光四种），不合法就 `memmove` 左移一个字节继续扫描。
> 不需要帧头同步字，字节流错位后最多丢弃 19 字节就能自动恢复；后来新增两种帧类型时状态机一行没改。
>
> 第二，**安全二进制解析**。多字节字段统一用 `memcpy` 读取而非指针强转，避免 ARM 上未对齐访问触发 SIGBUS。
>
> 第三，**双线程周期控制**。发送线程 `clock_nanosleep(CLOCK_MONOTONIC)` 定时（可选 `TIMER_ABSTIME` 绝对模式消除累积误差），
> 接收线程阻塞 recv 喂入状态机；退出用 SIGINT/SIGTERM 置 `volatile sig_atomic_t` 标志 + `goto cleanup`。
> 期间定位并修复过一个真实缺陷：对端静默时 `recv` 永久阻塞导致 `pthread_join` 挂死，解决办法是 join 前先 `shutdown`。
>
> 第四，**真实传感器接入**（用户态）。读 `/sys/bus/iio/devices/iio:deviceN/*_raw`：
> 按 `name` 定位设备（编号会变，不能写死）、属性 fd 常驻 + `pread` 复用（每帧系统调用 21→7 次）、
> 线上只传 int16 原始值、换算系数收发共用一份宏。板端实测 100.03 Hz、2741 帧零丢帧、温度 34.6 ℃ 稳定。
>
> 项目零外部依赖，`make arm` + `make deploy` 即可交叉编译部署到 i.MX6ULL（ARMv7 / Linux 4.1.15）。

### 11.3 3 分钟版本（技术深度版）

> （前 1 分钟与上面相同，展开部分如下）
>
> **关于粘包状态机的设计抉择**：TCP 是流式协议，send 和 recv 之间没有消息边界。常见方案有定长帧、帧头+长度前缀、帧头+帧尾标记。我们这个场景帧长固定 20 字节，但帧头**不固定**——UWB 帧头是 `'u'`、车体状态帧是 `'c'`、IMU 帧是 `'i'`、环境光帧是 `'a'`——所以用帧头识别需要在四种模式间切换。我选择了**帧尾同步**：帧尾两位固定是 0x55 0x56，无论哪种帧都统一。滑动窗口的 `memmove` 在帧边界错位时把缓冲区左移一位、写指针退到 19，本质是丢弃最早到达的字节。这比"找帧头→读定长→验帧尾"更鲁棒，负载里出现帧头字节也没关系。后来加 IMU / 环境光两种帧时，只加了两个分派分支，状态机本身一行没动——这是这个取舍带来的可扩展性。
>
> **关于 memcpy 而非指针强转**：这体现了嵌入式开发中对平台差异的关注。在 x86 上指针强转能工作，但 ARM 要求 int32 和 float 四字节对齐。uint8_t 数组只有单字节对齐保证，buf+2、buf+6 这些偏移不是 4 的倍数时，直接 `*(float*)(buf+6)` 会触发 SIGBUS。`memcpy` 在 glibc 中会处理未对齐的情况，而且编译器通常将它内联为单条加载指令——既安全又不损失性能。
>
> **关于 tcp_send_all 的 EINTR 和 MSG_NOSIGNAL 处理**：这两个细节很多网络程序会忽略。EINTR 是因为进程收到信号时正在执行的慢速系统调用会被中断，如果不重试就丢失了一次发送机会。MSG_NOSIGNAL 防止对端突然关闭时内核发 SIGPIPE 把进程杀死。我还额外在 main 中忽略了 SIGPIPE 信号做双重保险。`tcp_close` 也是先 `shutdown(SHUT_RDWR)` 后 `close`——shutdown 确保对端收到 FIN，close 释放描述符，防止资源泄漏。
>
> **关于真实传感器这一段的分寸**（容易讲过头，务必按这个口径）：驱动是板端既有的
> `icm20608.ko` / `ap3216c.ko`（IIO 驱动）。我做的**不是写驱动**，而是在用户态读它们导出的 sysfs
> 属性。可以讲"IIO 子系统 + sysfs 用户态读取 + 常驻 fd 复用"，**不能讲**"我写了 ICM20608 的 SPI 驱动"。
> 另外采样是用户态轮询（周期 p99 10.375 ms、最坏 46.8 ms），不是中断触发，**不能说硬实时采样**。
>
> **项目现状**：核心 TCP 通信与协议解析完成，并已在 i.MX6ULL 上实测（周期调度 4741 样本 + 真实传感器 3015 帧）。
> 自动化测试有 19 类协议用例 + ASan/UBSan。README 里规划的串口通信、V4L2 摄像头、MQTT 遥测、自动重连
> 等扩展方向**仍未实现**；真实机器人（执行器）闭环也没做——目前只有真实传感器，没有真实执行机构。
