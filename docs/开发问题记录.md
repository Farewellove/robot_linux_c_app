# 开发问题记录（真实踩坑 / 原因 / 解决）

> 记录本项目开发与联调过程中**实际出现过**的问题，每条都带现象、根因和验证方式。
> 只写有代码或实测数据支撑的条目，不做"当时很顺利"式美化。
> 本文件是项目的问题记录，随项目一起维护；`scripts/make_source_bundle.sh` 会把它并入单文件包。

---

## 1. 并发与退出

### 1.1 Ctrl+C 退不掉，只能 kill -9

- **现象**：对端只连接不主动发数据时，按 Ctrl+C，进程 6 秒后仍未退出，必须 `kill -9`。
- **根因**：`receiver_thread` 阻塞在**无超时的阻塞式 `recv()`**（`src/robot_tcp.c`）上。
  SIGINT 由内核投递给"任意一个未屏蔽该信号的线程"，如果被主线程或 sender 收走，
  receiver 并不知道要退出，仍卡在 `recv`；`main` 里的 `pthread_join(receiver)` 于是永久挂起。
- **解决**：`pthread_join(sender)` 之后、`pthread_join(receiver)` 之前调用
  `shutdown(g_sockfd, SHUT_RDWR)`（[src/main.c:457](src/main.c#L457)）。
  内核让阻塞中的 `recv` 立刻返回 0，receiver 自行退出。
- **为什么不选别的方案**：加 `SO_RCVTIMEO` 会改变 `recv` 的返回语义（要新引入 `EAGAIN` 分支），
  改非阻塞 IO 要重写接收逻辑，都不如退出路径加一行安全。
- **验证**：A/B 实测 —— 修复前 6 s 仍未退出（判为挂死，`required_kill9=yes`）；
  修复后 **0.102 s** 干净退出。复现脚本 `run_sigint_hang_test.sh`（只给主进程发 SIGINT，
  5 秒内未退出即判挂死）。对照组必须是**修复前**的二进制：用
  `git worktree add --detach /tmp/orig_app <基线commit>` 单独签出并构建，
  绝不能拿改过的代码当基线（理由见下面"用我改完的代码当基线"那条）。

### 1.2 console 输出被"拼接"了

- **现象**：日志里出现 `[CAR] ... vyrecv: connection closed by peer` 这种半截行。
- **根因**：`on_parsed_frame` 里的 printf 有 `g_print_mutex` 保护，但 sender 线程和主线程的
  printf **没有加锁**，两个线程同时写 stdout 时字节交错。
- **处理**：只影响可读性，不影响协议与数据，属于"已知无害缺陷"，在此如实记录，未顺手改。

## 2. 定时与周期性

### 2.1 10 ms 周期会"越来越慢"

- **现象**：目标是 10 ms 发一帧，实测周期总比 10 ms 大一点，而且误差逐周期累积。
- **根因**：发送线程用 `clock_nanosleep(CLOCK_MONOTONIC, 0, &req, NULL)`，`flag=0` 表示
  **相对睡眠**——每轮睡完再干活，实际周期 = 目标周期 + 本周期组帧/send 的耗时。
  源码里也没有保存"目标时刻"基准，所以基线数据**无法算出唤醒延迟**。
- **解决**：新增可选 `--abs-timer`，以线程启动时刻为基准维护 `next_sched_ns`，改用
  `clock_nanosleep(CLOCK_MONOTONIC, TIMER_ABSTIME, ...)`；默认仍走相对睡眠，保证既有行为与口径不变。
- **教训**：测出来的"周期抖动"必须区分是**业务耗时**还是**调度唤醒**。
  PC 离线基线：组帧+发送 p99 ≤ 79.8 µs（最恶劣 4.0 ms），而约 8.9%（888/9999）的周期被 CFS 推迟 >1 ms
  ——抖动主要来自调度，不是代码慢。
- **板端口径**（i.MX6ULL 4.1.15 单核，4741 样本）：工作耗时 mean 88.2 µs / p99 143.0 µs；
  周期偏差 mean 194.6 µs / p99 263.0 µs / max 489.3 µs，且**恒为正**，印证相对睡眠不补偿工作耗时。

### 2.2 用户态读 sysfs 不是硬实时

- **现象**：板端 IMU 采样平均 10.000 ms，p50 9.999 / p90 10.215 / p99 10.375 ms，
  但最坏一次 **46.838 ms**（2740 个间隔里唯一一次 >12 ms）。
- **根因**：每帧要读 7 个 sysfs 属性 + `clock_nanosleep` 定时，全靠用户态轮询，
  被调度或其它负载打断就会晚一拍。
- **处理**：不引入 `SCHED_FIFO` / `mlockall`（需要 root 且会改变运行语义），
  作为能力边界写进文档：要更高确定性，得靠驱动侧中断/FIFO 触发。

## 3. 协议设计

### 3.1 20 字节定长帧装不下 IMU + 光照

- **约束**：上下行都固定 20 字节，帧头帧尾必须保留。ICM20608 六轴+温度按 int16 是 14 字节，
  加帧类型和帧尾只剩 3 字节，AP3216C 塞不进去。
- **考虑过的方案**：把加速度换算成 roll/pitch 塞进 `'c'` 车体帧——零协议改动，
  但语义失真、丢温度、还会挤掉真实车体字段。
- **最终方案**：新增 `'i'`（IMU）和 `'a'`（AP3216C）两种帧类型，解析侧按 `buf[0]` 分派，
  帧尾仍是 `0x55 0x56`。`'u'` / `'c'` 的解析函数一行未改，老对端行为不变。
- **附带决定**：线上只传 int16 原始值，物理量在解析侧换算，换算系数用宏定义在
  `robot_protocol.h`，收发两侧共用一份，避免两处系数漂移。

### 3.2 TCP 是字节流，粘包/半包必须自己处理

- **现象**：一次 `recv` 可能拿到 0.3 帧、1 帧或 3 帧。
- **解决**：20 字节滑动窗口状态机——写满 20 字节判帧尾 `0x55 0x56`，匹配则按 `buf[0]` 分派并把
  `wr` 清零；不匹配就 `memmove` 左移 1 字节重新对齐。
- **代价**：最坏要丢 19 字节才能重新同步，这是帧尾同步的固有成本。
- **验证**：10000 帧用固定种子（20261011）随机切成 1~17 字节的块喂进去，
  10000/10000 帧内容逐帧比对正确（用例 T05）。

### 3.3 帧尾合法但帧头不认识 → 静默丢 20 字节

- **现象**：载荷恰好让 `[18][19]` 等于 `0x55 0x56`、而 `[0]` 不是四种已知类型时，
  这 20 字节被无声丢弃，还可能吞掉紧随其后的真实帧起始字节。
- **根因**：协议只有同步标志，**没有长度字段、没有 CRC**，帧尾匹配即认为成帧。
- **处理**：约束是"不得改协议"。所以**不改**，而是用 T08 把这个行为固化成测试，
  并在报告里明确"不能宣称解析器零丢帧"。随机载荷下这种窗口概率约 1/65536。
- **反思**：如果还能改协议，第一件事应该是加 CRC16 + 长度字段——同步标志只能解决对齐，
  解决不了内容损坏检测。

## 4. 传感器接入（IIO sysfs）

### 4.1 设备号不能写死

- **现象**：同一块板子，`/sys/bus/iio/devices/iio:device1` 是 icm20608，
  `iio:device0` 是 ap3216c——和"先加载谁就先编号"的直觉相反。
- **根因**：IIO 设备编号取决于驱动注册顺序，跨次启动/换板都可能变。
- **解决**：遍历 `/sys/bus/iio/devices/*/name`，读内容做字符串匹配来定位设备，
  绝不硬编码 `iio:deviceN`（`src/iio_util.c` `iio_find_device()`）。

### 4.2 每帧 21 次系统调用太浪费

- **现象**：IMU 每帧要读 7 个属性；如果每帧 `open/read/close`，就是 21 次系统调用。
- **解决**：初始化时把 7 个属性 `open` 成常驻 fd，之后用 `pread(fd, buf, sizeof(buf), 0)` 重读。
  sysfs 在 pos=0 时会重新执行驱动的 `show()`，所以能拿到新采样值，系统调用降到 7 次 `read`。
- **注意**：句柄常驻意味着属性文件被删除/驱动重载后需要重新 open，代码里按"打开失败就报错退出"处理，
  不做静默重试。

### 4.3 `pread` 编译报"隐式声明"

- **现象**：只定义了 `-D_POSIX_C_SOURCE=200112L`（项目 CFLAGS 里的值），仍拿不到 `pread` 的声明。
- **根因**：glibc 里 `pread` 受 `__USE_XOPEN2K8`（或 `__USE_UNIX98`）保护，仅定义
  `_POSIX_C_SOURCE` 不足以打开该特性宏。
- **解决**：`sensor_robot` 的编译目标额外加 `-D_XOPEN_SOURCE=700`（Makefile 里的 `EXTRA`），
  只影响这个目标，不动上位机的编译选项。

### 4.4 内核没开 IIO 时驱动加载失败

- **现象**：`insmod` 报 `Unknown symbol iio_device_alloc`。
- **根因**：板端内核 4.1.15 的配置里没有 `CONFIG_IIO`（或相关子项）。
- **解决**：确认内核配置后重新编译内核/模块；`load_drivers.sh` 里加了预检并给出处置建议，
  避免别人按文档复现时卡在同一处。

### 4.5 没有硬件也要能自测

- **做法**：`sensor_robot` 支持 `--iio-root`，把根目录指向一棵手工造的假 sysfs 树
  （`mkdir -p /tmp/fake_iio/iio:device0 && echo icm20608 > .../name`），
  PC 上就能跑通"读传感器 → 组帧 → TCP 推送"整条链路，不必等板子。
- **收益**：协议改动先在 PC 上回归，板上只做最终验证，联调次数少很多。

### 4.6 传感器代码不能污染上位机

- **问题**：`iio_util.c` / `icm20608.c` / `ap3216c.c` 如果直接进 `robot_linux_app`，
  会改变二进制体积和既有行为，之前采的性能数据就不可比了。
- **解决**：Makefile 里 `APP_SRCS` 用 `filter-out` 把这三个文件排除，只链进 `sensor_robot`；
  上位机链接项零变化。

### 4.7 驱动未就绪时不能"读到 0"

- **问题**：`insmod` 是手工执行的，节点出现可能晚于程序启动；若直接把读失败当 0 上报，
  日志里会出现一批看似正常的全零数据，极难排查。
- **解决**：`sensor_robot` 先等待驱动就绪（默认 10 s，可用 `--wait` 调），超时打印排查提示并以
  **退出码 3** 结束；运行中单次读取失败则计数并**跳过该帧**，不发全零帧。

## 5. 日志与部署

### 5.1 单层 mkdir 建不出 `log/<项目名>/`

- **现象**：日志打开失败，`fopen` 返回 NULL。
- **根因**：`logger_open` 里原来是单层 `mkdir`，路径从 `log/` 变成 `log/robot_linux_c_app/`
  后父目录不存在，`mkdir` 直接失败且没检查返回值。
- **解决**：改成递归建目录（等价 `mkdir -p`），逐级创建并检查错误（`src/logger.c` `ensure_dir`）。

### 5.2 板端日志污染了别的项目

- **背景**：板端从 `/lib/modules/4.1.15/` 启动，这个目录是多个项目共用的。
  日志直接写在工作目录，会和 iio_bench、gt911 等项目的产物混在一起。
- **解决**：统一 `LOG_ROOT/<项目名>/`，覆盖顺序为
  **默认值 < 环境变量 `ROBOT_LOG_ROOT` < `--log-dir`**，板端脚本另支持 `BOARD_LOG_DIR`；
  `make clean-logs` 只清自己那一层。

### 5.3 每帧 fflush 的代价

- **现状**：日志是 `fprintf` + 每帧 `fflush`，落盘及时但高频刷盘；
  而且 `fprintf` 的返回值没有检查，磁盘满/写失败无法感知。
- **处理**：属于"原落盘语义"，本次只作为审计发现记录，没有改成批量刷盘
  （那会改变崩溃时最后几帧是否落盘的语义）。

### 5.4 实测原始数据不该进仓库

- **现象**：一次板端采集就产生 456 KB / 约 7.8 千行的 CSV，两次采集把仓库 diff 撑到上万行，
  把代码改动淹没在数据里。
- **处理**：删除原始 CSV/txt/log（体积大且可重新采集），**结论归档为一份简短的实测汇总**
  （环境 + 周期调度 + 真实传感器 + 复现命令，已内联在本文件开头"1. 导读"的实测结论表里）；
  `.gitignore` 增加对应模式防止再次误提交。教训：**原始数据是过程产物，结论才是交付物**。

## 6. 测量与验证方法上的坑

### 6.1 用"我改完的代码"当基线

- **问题**：要证明 `shutdown` 修复有效，必须拿**修复前**的二进制做对照，否则数字没有说服力。
- **做法**：`git worktree add --detach /tmp/orig_app <基线commit>` 单独构建基线二进制，
  同机同环境跑同一套脚本，A/B 数据各存一份原始文件。

### 6.2 测试解析器 ≠ 生产解析器

- **问题**：如果测试里复制一份解析逻辑，很容易"测试全绿、生产照错"。
- **做法**：Makefile 里测试目标直接编译 `src/robot_protocol.c` 生产源码，
  只额外链接一个轻量断言框架，不引入 cmocka/Unity 之类新依赖。

### 6.3 ASan 通过 ≠ 全程序无缺陷

- **坑**：`make test-asan` 的 `detect_leaks=1` 只覆盖"协议解析 + 测试代码"这条路径。
- **处理**：报告里明确写"不代表全程序已通过 ASan"，避免把局部结论说成整体结论。

### 6.4 SO_KEEPALIVE 不等于断线检测

- **现象**：以为开了 keepalive 就能发现拔网线，实测拔线后毫无反应。
- **证据**：soak 运行中 `ss -tiop` 显示 `timer:(keepalive,113min,0)`，即内核默认空闲 7200 s 才开始探测。
- **处理**：没有擅自改 `TCP_KEEPIDLE/KEEPINTVL/KEEPCNT`（会改变连接生命周期行为），
  而是写进能力边界：空闲断线要 2 小时级别才能发现，程序也没有断线重连。

### 6.5 "零丢帧"要按收发的绝对数量说

- **坑**：只说"没丢包"没有说服力，因为根本没核对过两端的计数。
- **做法**：板端 `sensor_robot` 退出时打印 `tx_imu / tx_ap / err_*`，
  PC 侧日志按帧类型统计行数，两边数字对得齐（2741 / 274 对 2741 / 274）才敢写"零丢帧"。

## 7. 一句话总结

真正花时间的不是"写功能"，而是这几件事：

1. **退出路径**这种平时不跑的分支，最容易藏挂死（`shutdown` 唤醒阻塞 recv）；
2. **定时的口径**要先想清楚（相对/绝对睡眠），否则测出来的数字自己都解释不了；
3. **硬件接口不要写死编号**，靠 `name` 匹配；能常驻 fd 就别每帧 open；
4. **协议缺校验就得承认缺校验**，把已知丢包窗口固化成测试用例，别在文档里吹"零丢帧"；
5. **没有基线就没有说服力**——保留修复前的二进制和原始数据，A/B 对比才站得住；
6. **读失败要显式报错，不要返回 0 假装成功**——假数据比报错难查一百倍；
7. **原始数据不入库**，结论留档，否则仓库会被 CSV 淹掉。
