# 真实传感器接入与实测记录

> 记录「把虚拟数据换成开发板真实传感器数据」这件事的设计、实现与实测结果。
> 范围只涉及本仓库（`robot_linux_c_app`）；板端目录里其它项目（iio_bench / gt911 / touch_sensor …）
> 的产物仍按它们自己的方式落盘，本文不涉及。

---

## 0. 一句话结论

板载 **ICM20608**（六轴+温度）与 **AP3216C**（ALS/PS/IR）通过 IIO sysfs 在用户态读取，
组包成 20 字节状态帧经 TCP 推送给上位机；真机联调 **27.4 秒、3015 帧零丢帧、零坏帧**，
IMU 实际采样率 100.03 Hz，周期 p99 = 10.375 ms。

---

## 1. 背景与选型

原先链路的数据源是 `mock_robot` —— 用公式生成的虚拟 UWB / 车体状态帧，
用来验证协议解析与时序是够的，但端到端跑的不是真实物理量。开发板上焊着
ICM20608（SPI，IIO 驱动）和 AP3216C（I2C，IIO 驱动），两者都已经在内核里注册为
IIO 设备，用户态只读 sysfs 即可取数，**不需要写新驱动**。

### 1.1 数据怎么接进来

| 方案 | 做法 | 取舍 |
|---|---|---|
| A. 板端做真实数据源 | 新增 `sensor_robot`：读传感器 → 组帧 → TCP 推送；PC/上位机原样接收 | 与 `mock_robot` 同角色，可直接替换对比；**采用** |
| B. 上位机本地采样 | `robot_linux_app` 加采样线程，本地读传感器写 CSV | 不走网络，验证不到协议与链路 |

结论用 A：`mock_robot`（虚拟）与 `sensor_robot`（真实）两个对端并存，
同一套上位机代码既能跑虚拟回归，也能跑真实数据。

### 1.2 20 字节帧怎么承载 IMU 数据

约束：一帧定长 20 字节，ICM20608 六轴+温度按 int16 就是 14 字节，
加帧类型与帧尾后只剩 3 字节，**装不下 AP3216C**。

| 方案 | 做法 | 取舍 |
|---|---|---|
| A. 新增 `'i'` / `'a'` 帧类型 | `buf[0]` 分派，帧尾仍 `0x55 0x56` | 现有 `'u'`/`'c'` 解析一行不改，向后兼容；**采用** |
| B. 塞进现有 `'c'` 车体帧 | 加速度换算成 roll/pitch、陀螺仪当 vx/vy/vz | 零协议改动，但语义失真、丢温度，且挤掉真实车体字段 |

## 2. 板端接口（IIO sysfs）

两个驱动都是 IIO 驱动，设备号取决于加载顺序，**必须靠 `name` 文件匹配**而不是写死编号：

```
/sys/bus/iio/devices/iio:deviceN/name      ← 内容 "icm20608" / "ap3216c"
/sys/bus/iio/devices/iio:deviceN/<attr>    ← 每次 read 触发一次硬件采样
```

| 传感器 | IIO 设备名 | 属性 | 换算 |
|---|---|---|---|
| ICM20608 | `icm20608` | `in_accel{0,1,2}_raw` | `raw / 2048.0` → g（±16 g） |
| | | `in_anglvel{0,1,2}_raw` | `raw / 16.4` → °/s（±2000 °/s） |
| | | `in_temp0_raw` | `raw / 326.8 + 25.0` → ℃ |
| AP3216C | `ap3216c` | `in_illuminance_raw` / `in_proximity_raw` / `in_intensity_ir_raw` | 板端驱动 scale 恒为 1，原始计数即显示值 |

实测时板上编号：`iio:device1/` = icm20608，`iio:device0/` = ap3216c —— 正好说明不能写死编号。

**为什么用常驻 fd + `pread`**：每次采样要读 7 个文件，若每帧 `open`/`read`/`close`
就是 21 次系统调用；`open` 一次后用 `pread(fd, buf, n, 0)` 重读（sysfs 在 pos=0 时
会重新执行 `show()`），降到 7 次 `read`。

## 3. 帧格式

### `'i'` IMU 帧（ICM20608）

```
buf[0]      'i'
buf[1]      0x00            保留
buf[2..3]   accel_x  int16  原始值
buf[4..5]   accel_y
buf[6..7]   accel_z
buf[8..9]   gyro_x   int16
buf[10..11] gyro_y
buf[12..13] gyro_z
buf[14..15] temp     int16
buf[16..17] seq      uint16 帧序号，溢出回绕
buf[18..19] 0x55 0x56       帧尾
```

线上**只传 int16 原始值**，物理量在解析侧换算（`imu_raw_to_physical()`），
换算系数以宏的形式定义在 `robot_protocol.h`，收发两侧共用一份，避免两处漂移。

### `'a'` AP3216C 帧

```
buf[0]      'a'
buf[1]      0x00            保留
buf[2..3]   als  int16      环境光原始计数
buf[4..5]   ps   int16      接近检测
buf[6..7]   ir   int16      红外
buf[8..15]  0x00            保留
buf[16..17] seq  uint16
buf[18..19] 0x55 0x56
```

### 与原有协议的关系

- 帧尾同步、滑动窗口粘包状态机、按 `buf[0]` 分派的机制**完全复用**；
- `'u'` / `'c'` 的解析函数一行未改，老对端接进来行为不变；
- 帧尾合法但帧头不属于四种之一时，仍按原语义静默丢弃该 20 字节。

## 4. 代码结构

| 文件 | 作用 |
|---|---|
| `src/iio_util.c` / `include/iio_util.h` | IIO 通用访问：按 name 定位设备、打开属性 fd、`pread` 读整数 |
| `src/icm20608.c` / `include/icm20608.h` | 六轴+温度读取，只产 int16 原始值 |
| `src/ap3216c.c` / `include/ap3216c.h` | ALS/PS/IR 读取，open 时缓存 scale |
| `src/robot_protocol.c` | `build_imu_frame` / `build_ap_frame` / `parse_imu_frame` / `parse_ap_frame` / `imu_raw_to_physical` |
| `src/logger.c` | 新增 IMU（8 列）、AP（4 列）两种记录 |
| `tests/sensor_robot.c` | 板端真实数据源（替代 `mock_robot` 的虚拟数据） |
| `tests/test_protocol.c` | 新增 T16 / T17 / T18，用例数 16 → 19 |

要点：

- **传感器模块不链进上位机**。`Makefile` 里 `APP_SRCS` 用 `filter-out` 排除了
  `iio_util.c` / `icm20608.c` / `ap3216c.c`，`robot_linux_app` 的体积与既有行为不变，
  之前的性能数据不受影响。
- `sensor_robot` 支持 `--imu-every` / `--ap-every` 分频（默认 IMU 每周期、AP 每 10 周期）、
  `--wait` 等驱动就绪、`--iio-root` 指向假目录做无硬件自测。
- `pread` 在 glibc 里受 `__USE_XOPEN2K8` 保护，只给 `-D_POSIX_C_SOURCE` 不够，
  `sensor_robot` 的编译额外加了 `-D_XOPEN_SOURCE=700`。

## 5. 日志目录规范

运行期产物一律落在 `<LOG_ROOT>/<项目名>/`，不许散落在板端工作目录
（`/lib/modules/4.1.15/` 是多个项目共用的目录，散落会互相污染）：

```
log/
└── robot_linux_c_app/
    ├── robot_log_<时间>.csv        上位机逐帧日志（UWB/CAR/IMU/AP）
    ├── 03_periodic_timing.csv      --benchmark 逐周期指标
    ├── mock_server.csv             mock_robot 统计（默认）
    └── sensor_server.csv           sensor_robot 统计（默认）
```

- 板端从 `/lib/modules/4.1.15` 启动 → `/lib/modules/4.1.15/log/robot_linux_c_app/`
- 覆盖顺序：默认值 < 环境变量 `ROBOT_LOG_ROOT` < `--log-dir`；
  板端脚本另支持 `BOARD_LOG_DIR`
- PC 侧量化交付物仍在 `performance_evaluation/{results,logs}/`（仓库内的证据，不随运行清理）
- `make clean-logs` 只清 `log/<项目名>/`

## 6. 真机实测（2026-10-13）

### 环境

| 项 | 值 |
|---|---|
| 开发板 | 正点原子 i.MX6ULL，`192.168.1.55` |
| PC | `192.168.1.66` |
| 内核 | 4.1.15（需开 `CONFIG_IIO`，否则 `insmod` 报 `Unknown symbol iio_device_alloc`） |
| 命令（板端） | `./sensor_robot -p 19090 --period 10 --imu-every 1 --ap-every 10` |
| 命令（PC） | `./output/pc/robot_linux_app -i 192.168.1.55 -p 19090 -e 0 -m 0 --period 10` |

### 结果

| 项 | 结果 |
|---|---|
| 帧数 | 板端发 IMU 2741 / AP 274；PC 收到 2741 / 274 —— **零丢帧** |
| 下行控制帧 | 收 2699 帧，坏帧 0，seq 跳变 0 |
| 读取/发送错误 | IMU 0、AP 0、send 0 |
| 采样周期（IMU） | 平均 10.000 ms；p50 9.999 / p90 10.215 / p99 10.375 ms；最坏 46.838 ms（2740 个间隔中仅 1 次 >12 ms） |
| 实际采样率 | IMU 100.03 Hz、AP 10.04 Hz |
| 温度 | 均值 34.61 ℃，全程漂移 -0.02 ℃ |
| 姿态 | accel 见 ±0.9 g，gyro 峰值 ±192 °/s（采集过程中板子被转动） |
| AP | als 均值 260（14–455），ps 0–7，ir 多为 0 |

数据位置：

- `performance_evaluation/results/board_sensor_imu_20261013_223355.csv` —— PC 收到的逐帧日志
- `performance_evaluation/results/board_sensor_server_20261013_223355.csv` —— 板端 `sensor_robot` 统计

### 判读

1. **数据是真的**：静置段 `az ≈ +1 g`、gyro 接近零偏，说明量纲换算正确（不是把原始计数当物理量）；
2. **温度可信**：34.6 ℃ 稳定不漂，片内温度高于室温属正常；
3. **零丢帧**说明 20B 帧 + 帧尾同步这套协议在真实链路上没有对齐问题；
4. **周期抖动是用户态轮询的固有代价**：每帧要 7 次 sysfs 读 + `clock_nanosleep` 定时，
   p99 10.375 ms 已经不错，但最坏 46.8 ms 说明偶尔会被调度/其它负载打断。

## 7. 已知边界与下一步

- **不是硬实时采样**：现在由用户态定时读 sysfs 驱动，不是传感器数据就绪中断。
  要更高确定性，需要驱动侧用中断/FIFO + 定时器触发，再配合 `SCHED_FIFO`。
- **未做零偏/温漂校准**：静止时 gyro 零偏约 -1.0 / +1.6 / -0.5 °/s，积分会漂移；
  真要做姿态解算必须先标定。
- **协议仍无 CRC**：`0x55 0x56` 只是同步标志，载荷损坏检测不到（老问题，未顺手改）。
- **AP3216C 量程**：板端驱动 scale 恒为 1，ALS 是原始计数不是标准 lux，
  换算系数未在协议里写死，等驱动修好量程再对齐。
